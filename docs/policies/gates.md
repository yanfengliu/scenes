## `npm test`'s evidence markers

It prints each gate's elapsed seconds too, so a log carries what each one cost. Those markers are plain substrings, so a tool that renames its summary line goes red until `GATES` in `tools/test.js` is updated.

A tool that exits 0 having done nothing used to be reported here as a pass, which is what `blackframe` and `record` did on every CI run until 2026-09-09.

## Renderers

A gate renders on the GPU unless its verdict depends on the CPU rasterizer; `shot` and `compare` are the only two where it does, and they have no switch at all. `<NAME>_GPU=0` forces one gate onto SwiftShader, `<NAME>_GPU=1` forces one onto the GPU, and `GATES_GPU=0` moves all of them — the gate's own variable wins, which is what lets CI say "software everywhere except blackframe".

`GATES_GPU=0 BLACKFRAME_GPU=1 ANIMATION_FRAMES=3 BLACKFRAME_VIEWS=1 RECORD=0 npm test` is that run, locally.

Asking for a GPU is a request: chromium falls back to SwiftShader where there is none, so the printed tag says `[GPU]`, `[software]`, `[SOFTWARE FALLBACK: the GPU was asked for and none was available]`, `[GPU, though software was asked for]` — which is what `shot` would print, and it now fails on it rather than writing a GPU frame to the contract — or `[UNRECOGNISED: …]` for a renderer string that names no device.

**One gate carries per-renderer limits**, `nudge`, because its whole reading is shimmer and a GPU and a CPU rasterizer do not shimmer alike; the limits are keyed on what the run got, never on what it asked for. Everything else reads the same on both, measured (2026-09-15) rather than assumed — including `animation`'s scored thresholds, which briefly carried a renderer margin until a review measured that the margin was pure slack on the renderer the gate now runs on. The whole exercise and its numbers: `docs/devlog/detailed/2026-09-15-gpu-gates.md`.

**How far apart the two renderers score one frame is not a constant of this repo, and it was being read as one.** Measured on four trees on 2026-09-17: SSIM's crossing is stable, the GPU reading 0.00080 to 0.00091 better everywhere, but cell distance's swung from 0.000103 better on the 2026-09-15 tree to 0.0000036 better on iteration 5's and 0.000069 WORSE on a tree with the ambient light moved — it changes sign with the scene. Nothing anywhere may size a limit from the single figure the 2026-09-15 line quotes; `npm run try` carries the measurement and the method, and `docs/devlog/detailed/2026-09-17-fast-arm.md` has the table.

## `npm run import-inert`

A tool's main block goes inside `if (isMainModule(import.meta.url)) { … }`, with `isMainModule` **imported from `tools/serve.js`**, never hand-built. It opens no browser, costs about 7 s, and runs first in `npm test`.

It exists because importing `tools/animation.js` started a full animation run on main until 2026-09-15, and importing `tools/test.js` ran the whole suite — seven tools had no main-module guard at all. Its other half is the evidence-marker check: this one catches a tool that runs when it should not, that one catches a tool that does not run when it should.

## Suite cost

The suite costs about 3.6 minutes on this machine, sequential: import-inert 4 s, shot 63 s (SwiftShader, the contract), compare 1 s, placement 11 s, namerules 9 s, clearance 32 s, animation 12 s, nudge 15 s, blackframe 43 s, record 28 s — **218 s in all**, measured 2026-09-16. An earlier run the same day over the same gates read 191 s, and one before `namerules` existed read about 168 s: the per-gate numbers move several seconds run to run with machine load, `shot` by twelve between those two runs, so treat any one of them as a reading and not a budget. It was 35 minutes until 2026-09-11 and about 10 until 2026-09-15; `shot` is now 40% of it and is the one gate that cannot move. Where the earlier difference went is in `docs/devlog/detailed/2026-09-11-suite-cost.md`, along with the measurement that says running the gates concurrently would take another 30% off and why it was not taken — a saving worth much less now that only `shot` and `record` are long.

## Scene ready

The ceiling is what a slow shared runner needs and costs a fast machine nothing; a page that fails to load a script or throws still fails at once. The wait awaits `index.html`'s own `window.__sceneReady` in one evaluate rather than polling `window.__sceneState`, so the number is when the scene became ready and not when a poll next got a turn.

## Round-trips to the scene page

Image work never belongs there at all: `openInspector` in `tools/lib/browser.js` opens the blank page that every decode, resample and compose runs on, and it collects that page's errors into the caller's own array so moving work off the scene page does not move it out from under `collectErrors`.

**Two numbers, and they are not the same number**: the FRAME at 1200x1100 on this machine's SwiftShader is about **5.0 s** (composer target 1440x1320 at 4 samples — the shipped 8, clamped), and a ROUND-TRIP to that page costs about **14 s**, because the evaluate waits out the frame in flight and then its own, plus CDP. The 5.0 s is corroborated twice outside the probe that measured it: `animation`'s own per-frame line reads `pose and two frames 15.4 s`, which is `setTime`'s render plus two loop frames, and the whole `shot` path (one evaluate of two rAF, then a compositor screenshot) is 36.0 s. On a shared runner both are several times larger; on this machine's GPU the frame is about 5 ms.

**What the 5.0 s is spent on is not known** — two attempts to break it down both died on the same three.js fault, `Invalid value used as weak map key` in `WebGLState.drawBuffers`, reached by touching `renderTarget.samples` or `composer.setSize`; the second attempt's control row then read 0.02 s against its own 5.01 s baseline and the whole table was void. A third attempt should toggle `Pass.enabled` only and re-assert the baseline after every toggle. So the rule bites on the software rasterizer and is nearly free on a GPU — which is why moving the gates to the GPU on 2026-09-15 was worth more than every round-trip saving before it, and why the rule still matters: CI is SwiftShader and always will be. A round-trip to that page is never free there, so a gate that is slow is asked how many evaluates it makes before anything else. The same `decodeImage` call on the same file in the same process cost **96.1 s on the scene page and 0.1 s on the blank one**, and returns the same 1,320,000 bytes either way — byte-identical, with the scores off them equal as doubles (`out/scratch/decode-purity.mjs`). `tools/animation.js` was doing eight of those on the scene page.

## `npm run placement`

`PLACEMENT_CHECKS` casts the photo camera's ray through each listed position and fails unless the first mesh hit is the named one (a piece built inside another, a canopy hiding a missing trunk). `GROUNDING_CHECKS` takes each listed object's own base, drops a ray, and fails when the mesh it should stand on is too far below it (floating) or too far above it (buried). Both lists are in `src/layout.js`.

Both halves are cast in one `page.evaluate`, with the clock pinned first inside it; `clearance` pins its clock inside its own measuring call for the same reason.

**Renderer: the GPU**, and it waits for no settling frames, because no pixel enters the verdict — both halves are `THREE.Raycaster` against the scene graph on the CPU. Measured on 2026-09-15: the same 21 forward hits and 10 grounding results on both renderers, 7 s against 26 s standing alone (8 s in `npm test`, against 30 s before). Iteration 3 then grew `PLACEMENT_CHECKS` to 23, and re-measured on 2026-09-16 both renderers print 23 forward hits and 10 grounding results, 10 s against 24 s.

## `npm run namerules`

Updating is `node tools/namerules.js --update "<why>"`; the reason is required and must differ from the recorded one.

A mesh name is an interface between rules that were written apart and do not import each other: `PLACEMENT_CHECKS` in `src/layout.js` matches by name PREFIX, and `NO_CAST` in `src/lighting.js` is a name regex deciding which meshes cast shadows. Iteration 4 renamed `far roof ridges` to `far house ridges` to stop it widening the first, which moved it across the second and put 37 instances into the shadow pass; the shot went 364 to 366 draw calls and **every gate stayed green**, because `placement` only asks that the check still passes, `shot` prints the draw count and asserts nothing, and `perf`'s budget is 400. The only signal was a two-call move in a printed number, and it was explained away in writing before a second critic round decomposed the frame.

**53 rules** are pinned today: `NO_CAST`; `clearance`'s own `WALK`, `TERRACE`, `TERRAIN`, `LIVING`, `CANOPY`, `SURFACE_WORDS`, `PLANT_WORDS` and `BEYOND_BLOCKERS`; clearance's inline `o.name === 'cherry trunk'` lookup; and one population per `PLACEMENT_CHECKS` entry (23) and two per `GROUNDING_CHECKS` entry (20, its object name and its ground prefix).

**The rules are read out of their own files and evaluated, never re-implemented** — `NO_CAST` is a `const` and clearance's lists are locals inside a `page.evaluate` argument, so neither can be imported; the tool takes the text of the single-line `const NAME = …;` declaration and builds it with `new Function`, records that text in the manifest so an edit that moves no population is still red, refuses a `g`/`y` regex whose `lastIndex` would make the answer depend on the order names were tested, and **counts every `const <ident>` binding in the file first, in any shape, refusing unless there is exactly one** — a critic showed that counting only single-line declarations let a rule reformatted across lines go unnoticed while a stale one-liner left in a comment or a template literal was read and reported instead, green. The populations come from the BUILT scene, in one `page.evaluate` that returns every mesh's name, `castShadow` flag and instance count.

**The two halves cross-check each other where the defect lived**: every mesh `NO_CAST` matches must have `castShadow === false` in the built scene, so inlining a different regex at the application site is red (23 meshes named). It also asserts `shadowCasters`, the count `applyShadowFlags` returns — that is the term the rename moved, with no camera in it, and it is cross-checked against the meshes whose `castShadow` this run can actually see, because those are two different traversals. And it scans `src/*.js`, `tools/clearance.js` and `tools/placement.js` by line text for the five usual matchers plus any line that mentions a name and compares, splits or looks it up (**17 sites today, 14 of them mesh rules**; the other three match objects and a CSS colour), so a NEW rule nobody registered is red. That scan matched five method names until a critic found the rule it could not see — clearance's own `o.name === 'cherry trunk'`, in a file it already read — which made the gate's claim to cover every mesh-name rule false; taking every string method instead reached 41 sites, 20 of them `.replace()` on GLSL, so the widening is targeted at names rather than at strings. Bounds, and they are real: **one command rewrites the manifest**, so this makes a rename visible, not impossible — and that one command clears every class of finding at once, including a rule nobody registered, under a reason that may mention only the rename; it pins populations and not correctness, since a right rename and a wrong one move a population identically; the site scan does not cover this file, other tools or `tools/lib/`, and is still blind to a rule that holds the name in a variable spelled something else while using none of the five matchers; **every clearance rule is applied here independently while clearance classifies with a first-match-wins chain**, so `LIVING` is pinned at 23 where that gate builds 21, and reordering the chain moves clearance's real sets with this gate green; and draw calls and instance counts are printed and NOT asserted, because the first moves with frustum culling and canvas size and the second with the canopy's PRNG. Not proved red: the five floors, calibrated from the shipped figures and nothing else.

**Renderer: the GPU**, no settling frames, no pixel in the verdict; `NAMERULES_GPU=0` (or `GATES_GPU=0`) forces SwiftShader. Measured rather than assumed: SwiftShader prints the same 53 rules, 255 meshes, 98 shadow casters and even the same 370 draw calls and 745,206 triangles, so the manifest is a property of the scene and not the driver and CI is held to the numbers recorded here. About 9 s in the suite.

## `npm run clearance`

It writes `out/clearance.json`.

Both measure the built scene rather than the constants it was built from — it imports nothing from `src/` — because both defects it exists for were introduced by editing exactly the constants a source-derived check would have read.

**Headroom**: every blossom instance matrix, every strand vertex and every trunk vertex, against the paving found by a ray dropped under it. Nothing the cherry hangs may come below 1.90 m over the street or over the right terrace (a standing eye is 1.70 m, plus 0.20 m), and its low wood must all sit within 2.00 m of its own deepest point rather than being a limb at head height. The photo's blossom mask is a 2D silhouette and cannot bound depth, and the canopy once reached 1.71 m over the landing with every gate green.

**Street**: the paving's own bounding box is swept, the paved band's edges and centre found at each z, and both halves must keep 0.60 m of run clear of anything built between 0.35 m and 2.0 m over the paving, with the near half keeping 0.55 m clear of eaves as well. Each check also asserts it measured something, because a run that found a fragment prints the same word as a run that found the street: 40,000 canopy samples, 1,000 of them over paving, a trunk mesh and terrace paving existing at all, 50 structure meshes, a structure reaching the paving at a fifth of the street's z positions, and walkable paving under 90% of the sampled z between the swept window's top and z = -33.5.

**And it checks its own classification.** The building set is built by exclusion — anything the walkable, terrace, terrain, plant and canopy lists do not match is a building — and all of those are whole-name anchored regexes, so a new mesh is never near a match and a new PAVING or a new PLANT lands in the building set in silence. Iteration 3's `right walkway slabs` and `fence spill leaves` both did, for a whole iteration, with every assertion green; the terrace headroom rays were landing on the band under the flagstones, up to 1.02 m below the surface at the terrace's steep end. So every set is printed by name, the terrace among them since 2026-09-16, and a mesh in the building set whose own name contains a paving word or a plant word fails the gate. Its bound is real and is measured against the scene's own names rather than invented ones: it is a word list, printed every run and recorded in `out/clearance.json`, and over the sets that are correctly classified today it would catch only **WALK 6 of 14, CANOPY 1 of 2 and LIVING 7 of 33** — blind to `stairs`, `gutter`, `landing`, `far street`, `platform`, `cherry strands`, `cherry trunk`, `pot` and more, so `landing 2` or a fourth pot would still land in the building set in silence. It also looks one way only: a building misfiled as terrain or a plant is caught by nothing. `plant` is deliberately NOT one of the words, because `planter` is this repo's own name for the terrace's stone bed in eight places and that bed is masonry — the failure text would have told someone to move a real obstruction into the plant set. Add a word when a new name needs it, never to close the gaps above: a word added for a mesh nobody has written cannot be red-proved. One plant is a known, measured hole rather than an oversight — `fence spill leaves` hangs 1.44 m over the terrace by construction, so it is classed as a plant and printed, not asserted. Bounds are in the tool's header; the ones to know are that it excludes the petals (they are built to fall through the street, and a petal's drawn height is a shader function of the clock rather than its instance matrix), that it reads CPU matrices and so would miss a wind with a y term, that it asserts a clear RUN in each half rather than a clear half, that it measures the far row's wall line for the 0.60 m rule and its eave line for the 0.55 m one, and that the street stops at z = -33.5 — past there the corner house's roof oversails the last of the paving, which is the scene's own open defect, printed rather than asserted, with the exempt region pinned to no more than **6 rows and to `corner house roof` alone** so a NEW building there is red. That pin was 40 rows and three meshes until 2026-09-16, written when `far street slabs` ran to z -42 and 7.5 m of paved road lay under three buildings: 34 rows, 27 of them blocked. Iteration 4 ended the paving at the corner house's own front face and left 3 rows, 1 blocked, by one mesh — so the old pin was five times the region it guarded and a whole new building standing across the road inside those 40 rows would have passed the row count. 6 is 3 plus a stated margin of 3 rows (0.75 m), which is what the sweep's own 0.25 m grid and a small move of `FAR_STREET_END` can shift without anything being built. Both halves are red-proved: relaying the paving to z -42 fails on the row count **and** on `corner house body` and `bend roof` no longer being exempt, and that same mutation passes with exit 0 under the old 40-row, three-name pin.

**Renderer: the GPU**, and no settling frames either, for `placement`'s reason — it reads instance matrices, vertex positions and raycast hits, never a frame. Measured: every printed figure identical on both renderers, to three decimals and the same coordinates, 14 s against 24 s standing alone (12 s in `npm test`, against 21 s before).

## `npm run groundcover`

It opens the `whitehouse` scene URL, pins the clock, and drops one `THREE.Raycaster` ray straight down from y = 400 m on a 20 m grid over x +-640 m and z +-900 m (5,915 cells), failing if ANY cell's first non-sky hit is nothing, with a 5,000-cell floor and a floor of exactly one mesh named `sky` so a sweep that collapsed cannot read as a pass, and it imports no `src/whitehouse/**` module because the defect it exists for was a slab that was never where the source said.

**No scored metric can see a ground void**: `compare` reads sky through a hole as just another colour, and the pass that closed the first one — a 40.6 m by 1040 m trench the sky showed through — moved both scores the right way for entirely unrelated reasons, so this gate counts rays rather than pixels and was red-proved on the real defect before the fix (**4,166 of 5,915 cells blank**, green at 0 of 5,915 after). It is scene-scoped to `whitehouse` in `tools/test.js`'s `GATES` and is **skipped for every other scene with its reason printed** (the slabs it sweeps and the camera clamp its extent comes from are this scene's own, and scene 1's 30 m street is not a ground-cover question), the same generic skip path scene 1's own gates take in a `whitehouse` run; its bounds — a hole outside that box, narrower than one 20 m cell, or hidden under another mesh is not seen — are named in its own header.

## `npm run animation`

The shot gate pins the clock at t = 0, so it alone cannot see a drift that only shows once the canopy has swung. `ANIMATION_FRAMES` trims the list; the motion reading moves with the spacing and the `0.4` ceiling does not, measured at 0.15 levels over seven frames, 0.19 over three and 0.24 over two on the GPU (the default local run) and 0.14 / 0.18 / 0.22 on SwiftShader (CI), so a trimmed run sits nearer that ceiling and its number is not comparable to a full run's. Each frame prints what it cost, split into the pose, the screenshot and the decode. Rendering these frames smaller is not available: the gate holds the worst of them to `docs/PLAN-scores.md` plus 0.0006, which is the shipped frame's own threshold and belongs to the 1200x1100 contract — on SwiftShader the t = 0 frame is byte-identical to `out/render.png`.

**Renderer: the GPU, 11 s against 277 s** (`npm test`'s own lines), and the scored thresholds are the same on both renderers: on this machine's GPU the same frame scores about 0.0009 better on SSIM and within 0.0001 of the software frame on cell distance, so it sits inside the unwidened thresholds with at least as much room as a software run has. That sentence read "0.0001 better on cell distance and 0.0009 better on SSIM" until 2026-09-17, when the crossing was measured on four trees instead of one: SSIM's half held (0.00080 to 0.00091) and the cell half did not — it was 0.000103 better on the tree it was first measured on, 0.0000036 better on iteration 5's, and 0.000069 WORSE with the ambient light moved. It is a fact about a tree, not a constant, and it does not always favour the GPU. The cell headroom at iteration 5's score is 0.0015 (0.0611 against 0.05958), **14.8 times** the largest crossing in that set, and this gate adds its own 0.0006 allowance on top, which makes 20.6; either way its verdict is unaffected. (An earlier draft of this sentence said "more than twenty times" against the 0.0015 figure, which is false — 20.6 belongs to the other denominator, and a critic caught the two being mixed.) What the old wording would have done is let someone size a TIGHTER limit from a number that moves. See `npm run try` and `docs/devlog/detailed/2026-09-17-fast-arm.md`. A renderer margin was briefly added here and removed after a review measured it as pure slack; the note above `OUT_DIR` in the tool says why, and the point generalises — a widened limit is a limit nobody can red-prove. The worst frame is also held to this run's own t = 0 frame, which is a restatement of the spread bound anchored somewhere meaningful rather than a second bound. The spread and motion bounds never cared which renderer drew the frames, only that one renderer drew all of them.

## `npm run nudge`

It exists because a user saw the scene flicker while orbiting and no scored gate could see it: a still camera renders the same frame every time. The scene is rendered above canvas resolution (`POST.renderScale`) for the same reason.

**Renderer: the GPU, 10 s against 170 s, with its own limits** — this is the gate where the renderer was never neutral. The user had a GPU, and a GPU gets the eight multisamples SwiftShader clamps to four, so a SwiftShader run was comparing the supersample alone with the multisampling held at the broken value in both arms. On the GPU the same mutation separates ratio 1 by 5.1x where SwiftShader manages 2.2x, and the old limits would have let the broken scene pass ratio 1 outright. `LIMITS` in the tool is keyed on the renderer the run actually got, so a fallback to software is held to the software numbers and CI's verdict is unchanged.

## `npm run blackframe`

`BLACKFRAME_VIEWS=<n>` trims the sweep and the run prints which views it covered; CI runs one, the size the user's report came from.

It is the counterpart to `nudge`, which scores how much the frame *changes* and therefore rates a fully black frame as perfectly stable; this one scores whether the frame is *there*.

**Renderer: the GPU, and it is the one gate that asks even where the others are told not to** (`BLACKFRAME_GPU=1` beats `GATES_GPU=0`, which is how CI is written) — the defect it guards is a driver behaviour, so it asks wherever it runs, prints the renderer it got, and falls back to SwiftShader where there is no GPU. The two frames a resized view settles for are waited for inside the measuring call rather than in a `page.evaluate` of their own, which is the same frames and one round-trip fewer.

## `npm run shot`

That frame is the contract `docs/PLAN-scores.md` records, so nothing in the tool may change the pixels: hiding the page's chrome, pinning the clock and waiting two frames for the compositor are one evaluate rather than three, and the file is byte-identical either way (sha256 `d29b76dd0272…` on SwiftShader).

**Renderer: SwiftShader, and this is the one gate with no GPU switch at all** — the scored number has to be the same digits here and on a runner, and a CPU rasterizer is deterministic across machines while a driver is not. A flag that could move these pixels is a flag that could move them by accident, and the tool now **fails** rather than shooting if chromium hands it a GPU anyway — a GPU frame would score 0.0748 / 0.4742, inside the thresholds, and rewrite the contract on a green run.

**Since 2026-09-17 it also records and refuses the configuration the frame was drawn at.** The sidecar carries `post` — the rung, its cost, the scale, the target size, the sample count, the numbers `verifyComposer` measured (badTaps, meanLuma, referenceLuma, lightKept), the watchdog's counters (floor, ratchets, contradicted readings, and whether it has switched itself off), and how long the scene took to become ready — read out of `describe().post` as the last act of the evaluate the tool already makes, so it costs no round-trip, and printed. It **fails** on four things the contract frame must never be: a rung `src/post.js` does not mark as the chain AS DESIGNED, a watchdog ratchet, any `post:` warning the page printed, and a configuration that changed between readiness and the shot.

**The predicate is `designed`, not `rung === 0`**, and that is measured rather than stylistic: the rung is an index into the rungs that fit the memory budget at this size, so on a large high-density window index 0 of what survives is already a lesser chain, and a gate that asked for index 0 would have written it to the contract (red-proved with `TARGET_BYTE_BUDGET = 1`). Those are four ways of asking one question because each is blind somewhere — the rung is a number the page reports about itself, the warning is a string `src/post.js` could stop printing, and the pair only differ if something re-tuned inside the tool's own window. The five rungs available at 1200x1100 on SwiftShader produce five different files (`e95a53185ee3`, `1f74009907c0`, `1825c9dd2e0f`, `d1d5527ad529`, `e11e4d5135b8`), so a step-down really does rewrite the contract.

**And it has already caught one**: 1 of 25 fresh runs of this tool on this machine ratcheted its watchdog on a healthy frame and drew `1f74009907c0`; that cause is fixed in `src/post.js` and this refusal is what makes the next one of its kind red instead of scored.

**Its bound is stated in the tool's header and is large: it did not catch the flake it was written for.** The 2026-09-17 frame that scored 0.0632 instead of 0.05958 from the same tree was drawn at the designed rung with the right size and samples; what separates it is the recorded verdict (referenceLuma 54.6 and meanLuma 72.7 against 57.5 and 76.8). No ABSOLUTE figure for that is asserted anywhere, because the light in this scene is a property of the scene and an iteration lane moves it every iteration; what asks the question is `compare`'s same-tree light check, below. The refusal covers the configuration; the record covers the diagnosis. `docs/devlog/detailed/2026-09-17-shot-rung.md` has the whole measurement.

**And since later the same day it refuses the LIGHT as well**, which is the half aimed at that flake rather than at its neighbour: the sidecar carries `env` out of `describe().env` — the map's own radiance, its shape, the per-material binding and what it adds to the photo view — and this gate fails when `src/lighting.js` could not prove the map, or when it had to build the map more than once. That second one refuses a frame that may be byte-identical to the contract, deliberately: a first build that carries no light is the 2026-09-17 event happening on this machine, and a green run would bury it. Both cost no round-trip; they ride the evaluate this tool already makes. Proved not to move a pixel — `out/render.png` is byte-identical across the change, sha256 `ef7a32617aa6f91f` on SwiftShader. It is 64 s of the 161 s suite and it stays there.

## `npm run compare`

It refuses a render older than the source. It writes `out/compare.png` (photo | render | 50% overlay | heat-map), `out/overlay.png` (the plan's landmark boxes over a 50% blend at 1200x1100), and `out/scores.json` (scores plus per-cell means, the tree the render came from, and the post-chain and environment state it was drawn at).

Bound of the compare scores: they see 528 mean colors and a 64 px grayscale image, so a landmark 10 px off in the photo is invisible to them. `out/overlay.png` is the check for placement.

**Renderer: SwiftShader, no switch either, for a different reason than `shot`'s** — it renders no 3D at all, but it decodes and resamples both images through chromium's 2D canvas, and an accelerated canvas would make the scored digits a property of the graphics driver. On this machine the decode came back byte-identical either way; the lever is absent because the measurement covers one machine and the contract covers every machine.

**It refuses nine things, not one**: a render older than any source file (by mtime, which is the 2026-09-05 rule), a missing `out/render.tree.json`, a sidecar whose recorded render digest is not the `out/render.png` on disk, a recorded scene source tree that is not the tree on disk, a sidecar with no post-chain state or no verdict inside it, one whose post-chain rung `src/post.js` does not mark as the chain as designed, a sidecar with no environment state or one of a shape it does not know, and one whose environment map `src/lighting.js` could not prove or had to build twice — the second, third and fourth are the score's half of the binding that replaced `1-photo.png` being byte-identical to `out/render.png`, and they catch what an mtime cannot: a source reverted to an older copy, a checkout that rewrote mtimes, a render carried in from another tree. The fifth and sixth are the 2026-09-17 POST half: the thresholds in `docs/PLAN-scores.md` are the FULL chain's numbers, and a frame drawn at a lesser rung scores differently while looking, in every other field of the sidecar, exactly like the contract. Their bound is that they read a number the page reported about itself, and that they are blind to the flake they were written for, which was drawn at rung 0. The seventh and eighth are that day's LIGHT half and are not blind to it: the thresholds are also the fully lit scene's, and the frame this scene draws without its environment map scored 0.0632 against 0.05958, which fails them.

**And a ninth check is aimed at that flake's own class from the other side: the same tree must draw the same amount of light.** When the previous `out/light-anchor.json` is of the same scene source tree, its `referenceLuma` — `verifyComposer`'s own 64x64 render of the scene with no post chain, at a clock pinned to 0 — is the anchor, and this run must land within 0.15 of it; the 2026-09-17 flake moved it 2.9 (57.5 to 54.6, the figure that scene reads with `scene.environment` removed). Nothing is pinned: the anchor is whatever the last run of the same source measured, so an iteration lane that changes the scene resets it and nothing has to be maintained. Its bounds are real and printed: it needs a previous anchor OF THE SAME TREE, so a fresh clone and every CI run skip it and say which case they took — **and it would NOT have caught the 2026-09-17 incident itself**, which was the first `npm test` on a freshly merged main with no same-tree anchor; it catches every repeat. It says the two runs disagree and never which is right. The tolerance is 0.15, against a measured run-to-run jitter of ZERO over the 54 logged shot runs that recorded it, so it is one rounding step of a one-decimal figure and a twentieth of the 2.9 the defect moved. The anchor lives in its own file, written before the comparison decides anything, because keeping it in `out/scores.json` — which `compare` writes only after the check passes — would let one flake wedge every later correct run red against a stale figure. And it is blind to any change that moves no light.

## `npm run try`

**It is a diagnostic, not a gate**: it is in no suite, it asserts nothing about the scene and it has no threshold — and it **writes neither `out/render.png` nor `out/render.tree.json`**, only `out/try/render.png` and `out/try/score.json`, so it cannot feed `compare` and cannot become the scored record.

It renders the same photo view at the same 1200x1100 with the clock pinned at t = 0, scores it with the same `cellDistance` and `ssimGray` out of `tools/lib/metrics.js`, and prints the two numbers, the renderer it got, the scene source tree hash, the frame's sha256, the post-chain rung and its own seconds split by phase. What it does refuse are instrument faults, because an A/B is void without them: a page error, a frame not drawn by the post chain as designed, **a frame that did not get the sky’s environment map** (`src/lighting.js` proves that map and this tool refuses an arm whose proof failed, on exactly the grounds it already refuses a lesser rung — losing the map costs this scene about 0.0036 of cell distance, **36 times this tool’s own margin**, so an arm that lost it would read as a scene change and is not one), and the scene source changing under the run.

**Renderer: the GPU**; `TRY_GPU=0` (or `GATES_GPU=0`) forces SwiftShader, which is how an arm inside the margin is re-measured without leaving the tool.

**Cost: measured INTERLEAVED, GPU arm and software arm back to back three times, because this machine's load swings enough that two arms timed minutes apart differ by more than the renderer — 14/85, 14/90, 15/88 seconds, median ratio 6.1x, and 6.6x against the 93 s `npm run shot && npm run compare` in the same block. Those seconds are upper bounds under a named load; the ratio is the claim.** The split is the reusable number: on the GPU the frame work is 0.4 s of a 14 s arm and the other 12.1 s is the scene BUILD, against 42.5 s of frame work in an 85 s software arm — so what is left to attack is a build every gate that opens the page already pays.

**Agreement**: at `TRY_GPU=0` on the same tree its frame is byte-identical to `shot`'s (`e95a53185ee3…`) and its scores are equal to `compare`'s as doubles, not merely to four decimals.

**The margin, printed every run: 0.0001 of cell distance and 0.0001 of SSIM.** Below it an arm is too close to call on the GPU and goes back to `shot`. It is calibrated against the GPU-versus-software crossing measured on four trees, not against run-to-run noise, which is zero on both renderers here (11 GPU runs one sha256, 3 software runs one sha256). Bounds, and the first is the big one: the calibration is one machine, one driver and four trees that are all **one scene varied by one constant**, so a second scene with another photograph and another rig is outside it entirely and the offset must be re-measured there; the margin covers comparing two arms from THIS tool with each other and **never** a `try` number against `docs/PLAN-scores.md`, since a single GPU score carries the whole crossing rather than its variation; and like `shot` it is one frame at one clock, blind to the animation, to every other camera and to anything 528 cell means and a 64 px image cannot see.

## `npm run record`

`RECORD_SECONDS` and `RECORD_GPU=0` (or `GATES_GPU=0`) trim it and `RECORD=0` skips it with a printed reason; CI skips it, because on SwiftShader its 3007x1957 buffer had not finished after 19 minutes and would prove nothing about a GPU driver anyway.

It is the only gate that exercises the controls rather than posing the camera, and the only one that can see a flicker: the others sample moments. It also fails when it caught fewer than 30 frames, because too short a recording cannot tell a scene that never went dark from a recorder that never caught it.

**Renderer: the GPU, which it has always asked for** — the fault it exists for is a driver behaviour, and it is the only gate whose assertions are about real time, so it is also the one gate whose verdict could move with machine load.

## `npm run views`

There is no contact sheet: an aggregate view answers "is there one of each" and never "is each one right", so `out/views/index.txt` lists each pose's path, sha256 and mean luminance, plus one sweep digest over all seven to quote in a review, and the frames are reviewed one at a time at 1200x1100.

It poses the camera directly and does not exercise the controls, which is `npm run record`'s job, but it applies the same `clampCamera` a drag gets, and one pose exists only to prove that clamp fires. It found the top platform's bare face standing across the head of the stairs, which every scored gate passes over.

**Renderer: the GPU, 11 s against 291 s**, because nothing here is a verdict — it fails only on a page error and its whole output is frames for a person to look at.

**A sweep digest belongs to the renderer that drew it**: the same tree gives `b2e6a7395596` on the GPU and `beb2eef266b5` on SwiftShader, so a review quoting one is a review of that sweep, every digest quoted before 2026-09-15 is a SwiftShader digest, and the manifest names the renderer on its own line.

**And a digest only binds anything if it reproduces.** Until 2026-09-16 pose 7's did not: the frame loop runs `controls.update(); clampCamera();` every frame, that pose is the one the clamp corrects, and the clamp and the controls' polar limit take six of those pairs to agree while the two settle frames give the page's loop an unfixed number of turns — so the bytes landed on one of three files run to run. Each pose is now settled to a bit-exact fixed point of that pair before it is shot, and a pose that will not converge in 32 iterations is warned about by name and marked in the manifest, because the warning scrolls past and the manifest is what a review quotes. It was never only pose 7. Pairs that move the camera, pose 1 to 7: **0, 0, 1, 10, 0, 2, 6** — four of seven were being rendered unconverged and pose 4 is the worst of them; only pose 7 crossed a pixel boundary, which is why only pose 7 was reported.

**What binds the sweep to the score** is no longer that `1-photo.png` and `out/render.png` are byte-identical — they cannot be, since the two gates render on different rasterizers by design. The manifest now records the sha256 of the scene source these frames were drawn from (`index.html` plus `src/**`) beside each pose digest, `shot` records the same hash in `out/render.tree.json`, `compare` copies it into `out/scores.json` and refuses to score a render whose tree has moved, and `npm run treecheck` compares all three and fails when a sweep and a score are quoted as one tree and are not. Both tools read the hash before their first frame and again at the end, so "the tree held still" is checked rather than assumed. Elapsed seconds are printed per pose — every image operation after a pose is rendered runs on a second, blank page, because on the scene page under SwiftShader the render loop makes one `decodeImage` cost 80 s.

## `npm run treecheck`

It opens no browser and costs under a second. **It is not in `npm test`**, on purpose: `views` is a diagnostic, a fresh clone's first suite run has never produced a sweep, and a gate that went red for a missing diagnostic would be a false red.

Inside the suite it is `compare` that carries the same check for the half that always exists, failing when its sidecar is missing, when the sidecar's render digest is not the render on disk, or when the recorded tree is not the tree on disk. Bounds: it hashes `index.html` and `src/**` only, so a `tools/` edit or a CDN serving different three.js bytes moves no hash; **`japan.webp` is half of what `compare` scores and is bound by none of this** — it is in neither the hash nor `compare`'s mtime list, so a changed reference photo moves every score with no guard in this repo, and what binds it is its own bytes in git; it proves the artifacts agree about a tree and never that any of them is right; `docs/render.webp` is encoded from `out/render.png` without consulting the sidecar and so sits outside the binding too; and it reports a missing artifact as missing, prints how many pairings it actually made, and fails outright when no record carries a tree, so a run that compared nothing cannot read as a pass.

**CRLF is normalised to LF before hashing**, because this repo has `core.autocrlf = true` and no `.gitattributes`: hashing raw bytes made the hash a property of the checkout rather than of the commit — the same tree read `3811005047643b3b…` here and `dda00820d3825d48…` with LF — so a hash quoted in a review meant nothing across machines and a Linux re-run against artifacts made on Windows gave a false red naming every file. The cost is that a pure line-ending change is invisible to it, which moves no pixel.

## `npm run perf`

It launches chromium with the GPU (ANGLE/D3D11) and prints the renderer it got; `PERF_GPU=0` or `GATES_GPU=0` forces SwiftShader. CI does not run it: a shared runner's frame time says nothing about the budget. Measured here: 4.90 ms median at 1920x1080 on ANGLE/D3D11, which is the number the whole renderer decision rests on.

## `npm run shimmer`

`npm run shimmer` orbits the camera 0.1 degrees a frame through three poses at device pixel ratios 1 and 2 and scores the temporal second difference, `|2*F(i) - F(i-1) - F(i+1)|` as a frame mean and a worst 16x16 block, which cancels smooth motion and keeps pixels that toggle; a still control must read 0 or it exits 1, because a scene that changes with the camera and clock held still makes the figure meaningless. It is a diagnostic, not a gate: disocclusion at silhouettes sits under the figure as a floor, so the number compares builds on the same path and has no absolute threshold; it writes `out/shimmer.json`.

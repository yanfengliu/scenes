# 2026-09-17 — the scored frame was not deterministic: two causes, one fixed

`npm run shot` drew a different frame from the same tree. On main at `09eb339`, scene source tree `387c0513bdeda0a5`, the integration owner's `npm test` produced `0e56fc677faf` scoring **0.0632 / 0.5718**, which fails the 0.0611 cell-distance threshold. A `npm run shot && npm run compare` minutes later on the same tree produced `e95a53185ee3` at **0.05958 / 0.57134**, and a second full `npm test` produced `e95a53185ee3` again. Three good runs, one bad, one machine, one renderer string, the same 363 draw calls and 714,090 triangles.

The file name says "rung" because that was the hypothesis this work started from. It is wrong about THAT frame, and the measurement that killed it is the first thing below — and then a reproduction loop found a second, unrelated flake that IS a rung step-down, at 1 run in 25, and that one is fixed. Two mechanisms, and only one of them is settled. The short version:

| | what it is | reproduced | fixed |
| --- | --- | --- | --- |
| the frame this work started from, `0e56fc677faf` | the scene drawn with the environment map contributing nothing | no, in 56 shot runs and 7 fresh pages | no — the gates make it diagnosable and refuse its repeats |
| the flake the loop found, `1f74009907c0` | `watchPostChain` ratcheting the chain down on an unreadable drawing-buffer read | yes, 1 in 25 in the field, and deterministically by forcing the read | yes, `src/post.js`, proved on the forced read |

## The instrument first

Every number here comes off a worktree at `68ca098` whose `src/` is `387c0513bdeda0a5`, the flaking tree. Before anything was measured, `npm run shot && npm run compare` reproduced the good frame exactly — sha256 `e95a53185ee3595e`, 0.0596 / 0.5713 — so the control holds and the bad frame is the outlier, not the good one.

## What was believed, and what killed it

**The hypothesis handed to this lane:** the bad run's post chain settled on a lower rung of `src/post.js`'s ladder — either `verifyComposer` rejected rung 0 at build, or `watchPostChain` read a black sample once and ratcheted the floor — and `shot` wrote that frame to the contract. Three things pointed at it: the diff pattern is texture-scale with shifted silhouettes, the sky is untouched, and the bad run's `scene ready` was **13.7 s** against the 19–20 s of every good run. A cheaper chain is a faster chain.

**The measurement.** `tuneComposer(renderer, composer, { minRung: k })` forces each rung on a live page; `out/scratch/rung-sweep.mjs` drives `shot`'s exact path at each of them and `out/scratch/cells-match.mjs` scores every frame with `compare`'s own libraries. The cell columns below come from `out/scratch/cells-match-rungs.log`: `rung-sweep.mjs` printed a cell table of its own and **every figure in it is NaN**, because it compared a flat array of 1584 numbers against 528 hex strings. Its digests and post states are sound; its table is void and is not quoted anywhere. At 1200x1100 on SwiftShader the ladder dedupes to five rungs. They produce five different files, and **none of them is the bad frame**:

| forced rung | target | samples | sha256 | cells matching the BAD frame | cells matching the GOOD frame |
| --- | --- | ---: | --- | ---: | ---: |
| control (untouched) | 1440x1320 | 4 | `e95a53185ee3` | 63 / 528 | **528 / 528** |
| 0 | 1440x1320 | 4 | `e95a53185ee3` | 63 / 528 | 528 / 528 |

The number that settles it is the distance, not the match count -- the mean over the 528 cells of the WORST of that cell's three channel differences (`out/scratch/cells-match.mjs`), which is a stricter figure than a per-channel mean. Every rung sits **0.24 to 0.86** levels from the good frame — and **6.6 to 6.8** from the bad one, which is exactly where the good frame sits (6.742). A rung change moves the frame by a fraction of a level. Whatever drew the bad frame moved it by seven. The ladder is an order of magnitude too small to be the mechanism, and the control's `describe().post` confirms a plain run gets rung 0, 1440x1320, 4 samples, no ratchet.

## What the bad frame actually is

The difference is not geometric. `out/scratch/flake/diff-main1-vs-wt.png` shows whole surfaces filled with a flat, uniform difference — not bright lines at silhouettes, which is what a moved camera or a resampled resolution produces. The sky is **exactly** identical. Every lit surface is darker.

Per cell, over the 24x22 grid the score uses, the darkening is close to multiplicative in display terms: `bad ≈ 0.936 × good` on the **465** cells whose hex differs, coefficient of variation **0.041** for the ratio against **0.256** for the difference. The **63** identical cells all lie in rows 0–5, the sky wedge.

So it is a lighting difference. `out/scratch/knob-sweep.mjs` shoots `shot`'s path once per scene knob on one page, and `out/scratch/signature.mjs` correlates each knob's per-cell luma signature against the flake's (good minus bad):

**The environment map's contribution is what separates the two frames**, and nothing else measured comes near it. `src/lighting.js` sets `scene.environment` from a PMREM of the sky dome at `RIG.envIntensity = 0.12`.

**How close, exactly.** `env-null` differs from the flake frame on 112 of 528 cells, so it is not a byte match, and the obvious explanation was that the knob was applied to an already-built page whose lit materials then recompiled. That was tested and is **wrong**: removing the environment BEFORE the build, through `page.route` so the tree does not move, gives the identical digests -- `766c1dc55ec2` for `scene.environment = null` and `be81678686a0` for `environmentIntensity = 0`, exactly what the mid-run knobs produced -- and the identical 416 of 528 (`out/scratch/env-absent.log`).

So the residual is real, and it was measured rather than waved at (`out/scratch/residual.mjs`, `out/scratch/residual-cells.log`). Taking the environment term out of the flake leaves, over the 528 cells, mean 0.038 of a luma level and rms 0.422. It is not another light: correlated against every knob's own signature it reads 0.020 for the environment and between -0.11 and +0.04 for all ten others.

**And it is not spread evenly — splitting it by row is what makes it say something.** Over rows 3-21, 456 cells and 86% of the frame, the residual is **mean 0.002, rms 0.252**. The rms the 8-bit rounding of the two recorded cell means produces on its own is **0.306**, so over the great majority of the frame `env-null` and the flake frame are indistinguishable to the precision the recorded means carry. That is an identity, not a correlate.

The whole residual is in **rows 0-2, and mostly in columns 19-23**: mean 0.261, rms 0.950, and the five largest cells in the frame are (0,22) 5.00, (1,21) 3.28, (0,23) 3.21, (1,20) 3.00, (2,19) 2.79 -- the top-right corner, which is also where the flake darkened most (the good-minus-bad deltas at those same cells are 11.49, 9.78, 8.99, 8.64, 8.57). None of them is a cell the flake left unchanged, and none touches one, so it is not a sky-boundary artifact of the grid. In that corner the flake is darker than removing the environment accounts for, by up to 5 levels on cells whose own luma is 37 to 152. Everywhere else, the environment map is the whole of it.

The 13.7 s was read as corroboration and **should not have been**. `flake/suite-run1-head.log` is `shot` inside `npm test`, right after `import-inert` has spawned twenty node processes; the 19–20 s good runs are standalone `npm run shot`. Those two arms differ by more than the variable, and a fresh shell warms up by about seven seconds over its first three runs (26.0, 19.4, 18.3 in `out/scratch/shot-loop-run1-interrupted.log`). What DOES carry information is a fast outlier inside ONE loop, and there is one: see below.

## A SECOND nondeterminism, reproduced, and fixed

Running `npm run shot` as its own process with its own fresh chromium, 25 times over, reproduced a flake at run 18 (`out/scratch/shot-loop2.log`). It is not the 2026-09-17 frame, and it is a real one:

```
18: exit 1 ready 14.5s sha - DIFFERENT
      page: post: the frame has gone black at a 1440x1320 target with 4 samples, after that configuration
            had already been verified at this size. Stepping down and staying down.
      page: post: settled on a 1426x1307 target with 4 samples for this window size, giving up one percent
            of the supersample.
```

**`watchPostChain` ratcheted on a frame that was fine.** It reads nine single pixels off the DEFAULT framebuffer and, if all nine are under luma 24, steps the chain down permanently. Reading the default framebuffer back is not reliable — `tools/record.js` has documented for months that a drawing buffer read after the browser has composited can hand back cleared black through no fault of the scene — and this watchdog was treating one such read as proof.

The rate on this machine is **1 in 25 fresh shot runs, 4%**. That run's `scene ready` was **14.5 s against 18.3–28.0 s for the other 24** — the only run in the whole loop below 18.3, and the 2026-09-17 flake read 13.7 s, so both known bad events are faster than all ~80 good runs measured here. That is a TELL, seen twice, and not a mechanism: forcing the read black makes the run SLOWER than its control (33.0 s against 25.2 s), so nothing here shows that being fast causes the bad read. `shot` records `readySeconds` in the sidecar from now on, so the next hunt can sort by it instead of waiting for a wrong digest.

**It draws a different contract frame.** Forcing exactly one ratchet (`out/scratch/ratchet-frame.mjs`, rewriting two lines of `src/post.js` as it is fetched so the tree does not move) draws `1f74009907c0` — the same frame a forced rung 1 draws, and not `e95a53185ee3`. It is **not** the 2026-09-17 frame either: `0e56fc677faf` is no rung.

### The fix

A black reading is a trigger, not a verdict. `src/post.js` now asks two more questions before it ratchets: it runs `verifyComposer` at the CURRENT configuration, which reads the composer's own targets through `readRenderTargetPixels` and never touches the default framebuffer, and then reads the nine pixels again after that verification has drawn a fresh frame. Only if the targets are bad, or the canvas still reads black, does it step down. A contradicted reading is counted in `watch.falseAlarms`, announced with `console.log` and not `console.warn` — deliberately, because `shot` fails on a `post:` WARNING and announcing a frame that turned out to be fine as a warning would move the defect rather than remove it. After three contradicted readings the watchdog switches itself off for the page and says so: its input is noise on that machine, and a watchdog reading noise is worse than none.

Five arms, one page load each, on the same tree (`out/scratch/ratchet-frame-arms.log`):

| arm | what is forced | digest | rung | ratchets | false alarms |
| --- | --- | --- | ---: | ---: | ---: |
| control | nothing | `e95a53185ee3` | 0, designed | 0 | 0 |
| first-read-black | the first probe only | **`e95a53185ee3`** | **0, designed** | **0** | **1** |
| always-black | every probe | `e11e4d5135b8` | 4, not designed | 6 | 0 |
| every-first-read-black | the first probe of every call | `e95a53185ee3` | 0, designed | 0 | 3, then blind |
| first-read-black-and-bad-targets | the first probe, and `maxBadTaps: -1` | `e11e4d5135b8` | 4, not designed | 1 | 0 |

**Row two is the fix, and it is the evidence for it.** Against the code before the fix that exact arm drew `1f74009907c0` at rung 1 with one ratchet; against the code after it, the contract frame.

Rows three and five are the guard on the fix, and there are two of them because the ratchet branch has two ways in and the condition short-circuits. `always-black` forces the light reading false, so `verdict.ok` never enters the decision at all; the fifth arm leaves the probe alone after the first read, so the canvas reads LIT, and makes the VERIFICATION reject every frame instead. That is where the 2026-09-06 and 2026-09-07 faults live (the defect register records 53.9% of the frame not a finite number at that pose), and it still ratchets, in one call, to the bottom rung. The fourth arm is the give-up path.

**A bound the third arm states rather than hides**: `falseAlarms` only rises when the SECOND read comes back lit, so a driver whose default-framebuffer read returns black EVERY time never reaches the give-up path -- `always-black` records falseAlarms 0, blind false, and six ratchets to rung 4. An always-black read and a genuinely black canvas are indistinguishable here, and nothing in this module can tell them apart; what covers it is `shot` refusing the frame rather than trusting the chain.

**And the rate in the field, which is weaker evidence than the arms and is reported as such.** 25 fresh `npm run shot` processes before the fix: 1 not the contract frame. 25 after: 0. That is not a measurement of the fix. The chance of seeing zero failures in 25 runs at an unchanged 4% rate is **0.36**, the 95% upper bound on the post-fix rate from 0 of 25 is **11%**, and loop 3 may never have entered the regime at all -- its ready times span 18.1 to 20.6 s where loop 2 spanned 14.5 to 28.0 s with the flake at the only run below 18.3. What carries the fix is the forced arm, which is deterministic; the loops carry "no regression observed at n=25", and nothing more.

## The number that would have caught it, and it was already being measured

`verifyComposer` in `src/post.js` renders the scene at 64x64 with no post chain at all and records its mean luma as `referenceLuma`, beside the chain's own `meanLuma`. `out/scratch/reflight.mjs` reads both on a live page, removes the environment map, re-tunes, and reads them again:

```
on load:        {"badTaps":0,"meanLuma":76.8,"referenceLuma":57.5,"lightKept":1.337}
re-tuned as is: {"badTaps":0,"meanLuma":76.7,"referenceLuma":57.4,"lightKept":1.336}
env removed:    {"badTaps":0,"meanLuma":72.7,"referenceLuma":54.6,"lightKept":1.331}
env restored:   {"badTaps":0,"meanLuma":76.8,"referenceLuma":57.4,"lightKept":1.337}
```

57.5 against 54.6, and 76.8 against 72.7. Those numbers existed in `window.__scene.describe().post` on the day of the flake and **no gate wrote them down**. `shot` printed the renderer, the draw calls, the triangles and the tree hash — four things that were identical in the good runs and the bad one — and nothing about the light. That is the hole this work closes.

Note what `lightKept` does *not* do: 1.331 against 1.337. It is a ratio of two numbers that move together, so the chain's own verdict is blind to a scene that lost light before the chain ever saw it. A gate cannot be built on it.

## What is gated now

`shot` reads `describe().post` as the last act of the evaluate it was already making — after both settle frames, before the screenshot — and records it in `out/render.tree.json`: the rung, whether `src/post.js` marks it as the chain AS DESIGNED, its cost, the scale, the target size, the sample count, the verdict numbers, the watchdog's counters, and how long the scene took to become ready. It prints them. `compare` refuses a sidecar with no `post` or no `verdict` inside it, and one whose rung is not the designed one, and copies the block into `out/scores.json`.

`shot` also **fails** on four things the contract frame must never be: a rung that is not the chain as designed, a watchdog ratchet, any `post:` warning the page printed, and a configuration that changed between readiness and the shot. `src/post.js` counts the watchdog's ratchets so the second of those can be asked at all — `watch.floor` alone cannot answer it, because a ratchet followed by a re-tune back to an allowed rung leaves the floor where it was. The comparison drops the watchdog's counters before it compares, because a contradicted black reading moves one of them without touching a pixel.

**`rung === 0` is not the predicate**, and finding that out changed the check. The rung is an index into the rungs that FIT the memory budget at this size, and `ladder()` drops any rung whose targets would exceed 512 MiB — so on a large high-density window, index 0 of what survives is already a lesser chain. `src/post.js` now marks the designed rung itself and both gates ask for that. The red proof is `TARGET_BYTE_BUDGET = 1`: the chain reports **rung 0**, a 1200x1100 target with 0 samples, and `shot` refuses it. A gate that asked only for index 0 would have written that frame to the contract and passed. The `rung !== 0` branch that was there first is gone, because `designed` implies it on every ladder the dedupe can produce and no mutation could have reached it.

**And every gate now echoes what the post chain decided.** `collectErrors` in `tools/lib/browser.js` only ever looked at `console.error`, and `src/post.js` announces every step-down with `console.warn`, so **no gate in this repo could see one**: the scene could be drawn at a lesser configuration on any gate's page and every one of them would report a pass and print nothing. Three kinds of line are echoed now, at any console level — a `post:` step-down, a `post:` contradicted reading, and a `watchdog:` give-up — and exactly one of them is fatal, a `post:` WARNING, in exactly one gate, `shot`, whose frame *is* its configuration.

**And one check is aimed at the flake itself rather than at its neighbour.** `compare` takes `out/light-anchor.json`, and if it is of the same scene source tree, holds this run's `referenceLuma` to within 0.15 of the anchor's. No absolute figure is pinned anywhere: the anchor is whatever the last run of the same source measured, so an iteration lane that changes the scene resets it and nothing has to be maintained. The 2026-09-17 flake moved that number by 2.8 (57.5 against the 54.7 the same scene reads with the environment removed before its build). The tolerance is one rounding step of a one-decimal figure against a measured jitter of zero, and the skipped path prints which case it took, because a fresh clone has no anchor and **CI never has one**, so on CI this check does not run at all. Its other cost is arithmetic and is written into the failure text: because the anchor follows the last run, one flaked run produces TWO reds — the flake against the run before it, and the next correct run against the flake — and the third run is green.

The bounds are in each tool's own header, and the largest is stated there in as many words: **the rung refusals would not have caught the 2026-09-17 flake**, which was drawn at the designed rung. They cover a different member of the same class — a frame drawn at a lesser configuration and scored as the contract — which nothing covered before, which the five different digests above show is a real difference, and which the loop then produced in the wild at 1 run in 25. The same-tree light check is the one that covers the flake, and it covers it only from the second run of a tree onwards.

## What is not settled

**The 2026-09-17 frame itself.** The watchdog flake above is a second, independent nondeterminism found on the way; it is real, it changes the contract frame, and it is fixed — but the frame it draws is `1f74009907c0` and the one this work started from is `0e56fc677faf`, which no rung draws. So the mechanism behind that frame is still unproven. What is measured:

- Its signature is the loss of the environment-map contribution, at 416 of 528 cells exact against a baseline of 63 and a next-best knob of 68, and with a residual of mean 0.038 of a luma level that matches no other knob measured. Removing the environment before the build gives the same frame as removing it after, so that is not the residual either.
- It did not reproduce in 7 fresh pages in one browser, **56 fresh `npm run shot` processes** across three loops, or any of the individual verification runs. Fifty-four of those 56 recorded a figure and every one read referenceLuma 57.5; the other two were refused before they wrote one. The fresh pages also recorded environment-map mean 176.309 and 238 of 254 lit materials compiled against the current `scene.environment`.
- What it is NOT: not any rung, not the watchdog flake above (which draws `1f74009907c0`), not the exposure, the ambient, the hemisphere, the fill, the sun, the fog or either shadow knob.

What would settle it, in the order it should be tried:

1. **Leave `out/scratch/hunt.mjs` running and read its state on the first non-contract run.** It already records the three fields that separate the sub-hypotheses, and each is one field of one JSON: the environment map's own mean radiance (a black PMREM), `env.size` (a valid-looking texture whose `image.height` is 0, which makes the IBL lookup return black through `envMapCubeUVHeight`), and `litWithEnv` (materials compiled before `scene.environment` was assigned and never recompiled). No new code is needed.
2. **Prove the environment instead of assuming it**, which is what `src/post.js` already does for the post chain and what `src/lighting.js` does not do for the map it builds: render the map, look at it, and fail loudly if it carries no light. That is a change to `src/lighting.js`, which this lane is not allowed to touch, so it is a recommendation and not a change.

**Why no absolute figure for the light is asserted anywhere.** `referenceLuma` would catch this flake in one line, and pinning it would be the obvious gate. It is not pinned because the light in this scene is a property of the scene, an iteration lane moves it every iteration, and a pinned figure is one that someone has to raise — and would eventually raise past the defect. What is asserted is that two runs of ONE tree agree, with the previous run as the anchor; that resets itself when the scene changes and needs no maintenance, and its price is that it cannot run on a fresh clone or on CI, and would not have caught the 2026-09-17 incident itself, which was the first `npm test` on a freshly merged main.

**What a critic caught that this lane had not.** An independent read-only review of the diff and the claims returned findings that changed the code in five places and the numbers in four. The code: the `rung !== 0` branch was dead, because `designed` implies it; `collectErrors` would double-attach its console listener if a page were watched twice; `compare` dereferenced `recorded.post.verdict` with no guard, so a hand-edited sidecar would have produced a bare `TypeError` instead of a sentence; the same-tree light check kept its anchor in `out/scores.json`, which `compare` writes AFTER the check, so one flake would have wedged every later correct run red against a stale figure — it has its own file now, written before the comparison decides anything; and the tolerance was 0.3 against a measured jitter of zero, three times slack nobody could red-prove, now 0.15. The numbers: 458/70 changed and unchanged cells were really 465/63, the "0.223" coefficient of variation did not reproduce under any natural definition (it is 0.256), the residual column of the correlation table is an uncentred statistic printed beside a centred one, and `rung-sweep.mjs` printed a cell table that is entirely NaN. The review also read the running loop's directory listing and spotted the missing `tree-18.json` before this lane had looked at it, which is how the watchdog flake above was found.

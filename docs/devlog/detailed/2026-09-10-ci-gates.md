# 2026-09-10 — CI was green while two gates had never run

## What was believed and proved false

Believed: the remote gate ran the six, then seven, tools `npm test` names, and a green run on GitHub meant the scene had been through all of them on the runner.

False. `blackframe`, `record`, `paintcheck` and `shimmer` each guarded their main block with ``import.meta.url === `file:///${process.argv[1].replace(/\\/g, '/')}` ``. That expression is true on Windows and false on every POSIX `argv[1]`: `file:///` joined to `/home/runner/work/scenes/scenes/tools/blackframe.js` gives `file:////home/...`, four slashes, against the `file:///home/...` node actually sets. On Linux each of those tools imported its own module, ran nothing, printed nothing and exited 0. Two of them are gates in `npm test`, so CI reported them green from the day each landed, 2026-09-06 (`81584e9` for `blackframe`, `a7111cc` for `record`), until 2026-09-09.

The evidence is in run 34306122575, job 102323064914, on `c18673e`. `npm test` took 45m38s there and the tail of it reads:

```
03:57:12.5929434Z nudge: 6 poses stable across device pixel ratios 1 and 2
03:57:12.5989224Z == tools/blackframe.js ==
03:57:12.8927205Z == tools/record.js ==
03:57:13.1907618Z == thresholds (docs/PLAN-scores.md) ==
03:57:13.1909860Z PASS
```

0.294 s for `blackframe`, 0.298 s for `record`, nothing between them. Both banners come from `tools/test.js`; neither tool contributed a line. On this machine's GPU the same two gates take 19 s and 18 s, and on the runner's SwiftShader `blackframe` alone is minutes.

The rest of that run, banner to banner: shot 4m07s, compare 1.1 s, placement 2m13s, animation at three frames 27m53s, nudge 11m22s. Those are the real shape of the 45 minutes, and they are what the estimate in `.github/workflows/ci.yml` should be argued from.

Two smaller beliefs also died. A local run cannot see this defect at all — the old guard is *true* on Windows, so every tool ran here and the whole thing looked fine; the machine that could see it was the one nobody read the log of. And a green check mark on a run is not a claim about the run's attempts: run 34309378871 reads success today because attempt 2 passed, while attempt 1 of the same commit failed at `nudge` after 52 minutes.

## What moved, and from what

**The readiness ceilings, 90 s to 300 s** (`tools/lib/browser.js`). `openScene` gave both its phases 90 s. On `e725914`, attempt 1 of run 34309378871 (job 102332670039) died with `FAIL: scene did not become ready within 90000 ms` inside `nudge`, 52 minutes in, after `animation` had passed on the same runner; the identical code had passed an hour earlier on a faster one. Both numbers are now 300 s, the ceiling `ACTION_TIMEOUT_MS` already gave a single screenshot. They are ceilings, not waits — the poll breaks the moment the scene says it is ready — so a fast machine pays nothing, and a page that fails to load a script or throws before readiness still fails at once rather than at the ceiling. Every open now prints what it took: 11 to 17 s through SwiftShader at 1200x1100 locally, 2 to 4 s on the GPU. **The margin on a CI runner is not yet measured** — nothing printed it before this change, and the first run that will is the one after this lands.

**The evidence check in `npm test`** (`tools/test.js`). Gates are spawned with piped output, echoed live, and each is paired in a `GATES` table with the summary line only its finished success path prints. A tool that exits 0 without that line fails the suite, naming the tool and the missing text. Each gate's elapsed seconds are printed, so the next CI estimate can be read off a log instead of remembered. Seen red: see `docs/learning/gate-proofs.md`.

**The CI trims** (`.github/workflows/ci.yml`). `BLACKFRAME_VIEWS` 2 to 1, and `RECORD=0` added, because both gates now really run and both are expensive on a software renderer. `ANIMATION_FRAMES=3` is unchanged. The view kept is the first, 1280x720 at a device pixel ratio of 1.5 — the size the user's blackout report came from, and the only one no other gate visits.

**The local suite, measured from clean on this machine** (RTX 4090 for the two GPU gates, SwiftShader for the rest): shot 63 s, compare 1 s, placement 30 s, animation at seven frames 811 s, nudge 163 s, blackframe 19 s, record 18 s. 18m25s in total, exit 0. Scores 0.0812 and 0.4401 — the same two digits CI printed, which is the point of `shot` always taking SwiftShader. Read the seconds as an order of magnitude, not a benchmark: this machine runs several worktrees at once and another worker's gates were on it part of the time.

**The CI configuration, run locally** as `ANIMATION_FRAMES=3 BLACKFRAME_VIEWS=1 BLACKFRAME_GPU=0 RECORD=0 npm test` (the workflow does not set `BLACKFRAME_GPU`; chromium falls back on its own where there is no GPU, and forcing it here is the closer simulation): shot 51 s, compare 1 s, placement 36 s, animation 397 s, nudge 160 s, blackframe 73 s, record 0 s, `PASS`. 12 minutes, exit 0. `blackframe` at one view on SwiftShader costs 73 s here, and the post chain settles on 4 multisamples there against 8 on the GPU. Gate for gate, run 34306122575 was 3.7x to 4.8x slower than this machine on the same work — shot 51 s against 4m07s, placement 36 s against 2m13s, animation 397 s against 27m53s, nudge 160 s against 11m22s — which puts one `blackframe` view at 5 to 6 minutes there, and six views at half an hour. That is why the sweep is trimmed to one rather than left at six.

## The bound of RECORD=0 on CI

`record` is switched off on the runner, and that is a real hole with a real reason. The gate drives a 3007x1957 drawing buffer through 12 s of scripted mouse input; forced onto SwiftShader locally with `RECORD_GPU=0` it had not finished after 19 minutes and was stopped. That measurement was inherited, so it was retested at a third of the length: `RECORD_GPU=0 RECORD_SECONDS=3` had not finished after 16 minutes either, and the page alone takes 31.1 s to become ready at that buffer size on SwiftShader against 3.6 s on the GPU. The fault the gate exists for is a GPU driver behaviour that SwiftShader does not have, so those minutes would have proved nothing about the defect anyway.

That 31.1 s is also the sharpest argument for the new readiness ceiling: it is the slowest page this repo opens, on the same software renderer CI uses, on a machine 4x faster than the runner. The old ceiling was 90 s.

So: **the only gate that exercises the controls, rather than posing the camera, does not run on CI at all.** A flicker regression is caught by the local suite or not at all, and a commit whose only green run is the remote one has not been through it. The skip prints one line saying so, and that line carries the `record:` marker on purpose — the evidence check separates a decision in the log from silence, not a run from a skip.

Three smaller bounds from the same change. `blackframe` on CI visits one of six views and gets SwiftShader, so what it proves there is that the post chain is sound on the software renderer; the driver behaviour it was written for needs a machine with a GPU. The marker check proves a line was printed, not that a gate's checks are right. And two of the seven markers — `shot`'s `renderer:` and `animation`'s `spread over ` — are printed before their tool's own verdict, so they also appear in a run that then fails; that is harmless only because `tools/test.js` checks the exit status first and never reaches the marker check on a red gate. A future edit that moved either line earlier still, to before the work, would hollow the check out without breaking anything visible.

## What review caught in the work as it stood

The uncommitted change already carried the fix and the evidence check. Both run ids it cited as evidence were unusable as written.

The id in `.github/workflows/ci.yml` and `tools/test.js` was 34306122577, which is the **pages** workflow for that push — one 16 s deploy job with no gate output in it at all. The test workflow for the same push is 34306122575. Corrected, with the job id, so the 0.294 s claim can be checked by whoever doubts it.

The comment in `tools/lib/browser.js` cited run 34309378871 for the 90 s failure. That run reads as a success today: the failure is in attempt 1, and attempt 2, a re-run of the same commit, passed. The comment now names the attempt and its job, and says why the run looks green.

The guard fix itself was verified rather than assumed, because the mutation the proof needs could not be the literal old expression: it is *true* on Windows. Both forms were evaluated against a Windows-shaped and a POSIX-shaped `argv[1]` using node's own `path.win32`/`path.posix` and `fileURLToPath(url, { windows })` — old true then false, new true then true. The red proof then fed the old expression the `argv[1]` a Linux runner has, which reproduced the silent exit 0 exactly.

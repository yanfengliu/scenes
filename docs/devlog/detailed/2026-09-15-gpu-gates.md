# 2026-09-15 — every gate that does not need the CPU rasterizer moved to the GPU

This machine has an RTX 4090 and every gate in the repo rendered through SwiftShader, because `launch()` defaulted to it and nothing ever asked why. A 1200x1100 frame costs about 5.0 s there — and a round-trip to the scene page about 14 s, because the evaluate waits out the frame in flight and then its own — against about 5 ms a frame on the GPU. The suite paid that on every round-trip. Each gate now states which renderer it uses and why in its own header, and prints the renderer it actually got in the line `tools/test.js` reads as proof it ran.

Nothing about what any gate renders or measures moved, with one deliberate exception: `nudge` was re-baselined, because on SwiftShader it could not see half of the defect it exists for.

## The thing to read first: this change made a gate prove less, and the review caught it

The first version of it moved `animation` to the GPU and widened that gate's two scored thresholds there by a `RENDERER_MARGIN`, on the argument that a GPU does not produce SwiftShader's last digits. It read as caution. It was the opposite.

**The renderer crossing runs in the direction that flatters the GPU.** The same frame scores 0.074947 / 0.473324 on SwiftShader and 0.074844 / 0.474234 on this machine's RTX 4090 — better on both metrics. So the GPU run already sat inside the *unwidened* thresholds, and widening them gave the GPU path 0.0025 of cell headroom and 0.0082 of SSIM headroom where the software path has 0.0020 and 0.0055: **25% and 50% more slack, on the renderer the gate now runs on by default.** A gate proving less than it did at `3854c75`, wearing the costume of renderer-awareness.

**And it could never have been made to go red.** The mutation that reds this gate — `WIND.canopy` at fourteen times the shipped amplitude — reds the MOTION bound, and the scored pair prints `ok` straight through it, on both renderers. So no proof could reach the margin, and nothing would ever have found it. That is the exact shape the canon warns about: a margin nobody can prove, on the path the gate takes by default, is a gate that proves less while looking like more.

The margin is gone. Both renderers are held to `docs/PLAN-scores.md` plus `ALLOWANCE`, and the GPU run passes those unwidened numbers — `0.0749 <= 0.0769`, `0.4740 >= 0.4678` — which is the measurement that says the margin was never needed. A driver that crosses the other way now reds the pair, and the failure block says to re-run with `ANIMATION_GPU=0` before blaming the scene. A red that asks for a measurement beats a limit pre-widened for a driver nobody has seen.

The same review found two renderer strings that would have handed `nudge`'s RTX 4090 limits to a CPU rasterizer, and one of them can reach CI. Both are in "What a critic caught" at the end.

**Inherited work.** The first owner of this unit was killed by a usage limit mid-task; its worktree survived and its transcript did not. Everything in `tools/lib/browser.js` — `wantsGpu`, `isSoftwareRenderer`, `rendererTag`, `openScene`'s `settleFrames` — and the GPU switch in `animation`, `blackframe`, `clearance`, `nudge`, `perf`, `placement`, `record` and `views` is that owner's, as are the renderer sections in `clearance.js`, `placement.js` and `views.js`, the SwiftShader `views` baseline under `out/scratch/`, and the `npm run perf` reading that established the machine has a usable GPU at all. This session verified it, measured every claim it asserted, and added what it had not reached: `animation`'s renderer margin, `nudge`'s re-baseline, the CI configuration, `shot` and `compare`'s stated refusals, the red proofs and the scored-path measurements.

### placement and clearance: nothing to argue, so it was measured

Both read the scene graph on the CPU — `THREE.Raycaster`, instance matrices, vertex positions — and neither looks at a frame. Rather than rest on that, both were run on both renderers on the same tree. `placement` prints the same 21 forward hits and the same 10 grounding results. `clearance` prints every figure identical: `2.073 m`, the same blossom at `(-0.33, -2.23, -15.69)` over the same `landing slabs`, `0.87 m` and `0.86 m` of low-wood spread, `1.10 m` and `0.65 m` of clear run, the same 60265-of-66284 census, the same 34 exempt rows. Both also stopped waiting for `openScene`'s two settling frames, which exist to give the compositor a canvas to screenshot and are worth nothing to a gate that never screenshots.

### animation: the scored pair, and the margin that was added and removed

Four of this gate's six checks — two of spread, two of motion — compare its frames with each other and never cared which rasterizer drew them, only that one rasterizer drew all of them, which one page, one browser and one run guarantee. The other two held the worst frame to `docs/PLAN-scores.md`, and those thresholds were measured on SwiftShader. There are eight now.

**The first version of this change widened those thresholds on a GPU by a `RENDERER_MARGIN` of +0.0005 cell and -0.0020 SSIM, and an independent review showed the margin was pure slack. It is gone.** The argument for it read as caution — a GPU does not produce SwiftShader's last digits, so widen — and it was wrong because the crossing runs the *other* way: on this machine the GPU scores the same frame **better** on both metrics. With the margin, the GPU path had 0.0025 of cell headroom and 0.0082 of SSIM headroom where the software path has 0.0020 and 0.0055 — 25% and 50% more slack, on the renderer the gate now runs on by default. That is a gate proving strictly less than it did at `3854c75`, dressed as renderer-awareness. Worse, it was unprovable: the mutation that reds this gate reds the motion bound, and the scored pair prints `ok` through it, so the margin could never be made to go red and nothing would ever have found it.

Both renderers are now held to `docs/PLAN-scores.md` plus `ALLOWANCE`, unchanged. A driver that crosses the other way reds the scored pair, and the failure block names the renderer and says to re-run with `ANIMATION_GPU=0` before blaming the scene. **A red that asks for a measurement is the safe direction; a limit pre-widened for a driver nobody has seen is a limit nobody can red-prove.**

The relative pair holds the worst frame to **this run's own t = 0 frame**, on whatever renderer this run got.

**The relative pair cannot fail while the spread check passes, and that is stated where it is written.** The best frame is at least as good as the t = 0 frame, so `worst - t0 <= worst - best`, which the spread bound already caps at the same allowance. It is a restatement of the spread bound anchored somewhere meaningful, not a second bound — and it is the reason the absolute pair is still there rather than replaced by it. Replacing it, which is what "make that check relative to its own t = 0 frame" reads like on its face, would have quietly deleted the only check tying the set to the contract.

The spacing series was re-measured on the GPU and barely moves: **0.15 levels over seven frames, 0.19 over three, 0.24 over two**, against 0.14 / 0.18 / 0.22 on SwiftShader, with the `MOTION.max` ceiling of 0.4 unchanged.

### nudge: the gate where the renderer was never neutral

This is the finding worth the session. The gate exists because a user reported the scene flickering while they orbited. **That user had a GPU.** On a GPU the shipped chain gets eight multisamples; `clampSamples` cuts SwiftShader to four. So a SwiftShader run was comparing a 1.2x supersample at 4 samples against the broken 1.0x at 4 samples: it was testing the supersample alone, with the multisampling pinned at the broken value in *both* arms.

Moving it to the GPU without touching the limits would have been worse than leaving it. Measured, one tree, both renderers, the recorded mutation (`POST.renderScale` 1.0, `POST.samples` 4), mean drastic change:

| | ratio 1 fixed | ratio 1 broken | ratio 2 fixed | ratio 2 broken |
| --- | ---: | ---: | ---: | ---: |
| SwiftShader | 0.095 | 0.211 | 0.246 | 0.372 |
| GPU | 0.036 | 0.182 | 0.205 | 0.327 |

Against the old limits (ratio 1: 0.4 per pose, 0.2 mean) **the broken scene passes ratio 1 on the GPU outright** — 0.182 under 0.2, worst pose 0.39 under 0.4. It still went red overall, through ratio 2 alone, which is exactly the shape of a gate that has quietly lost half its coverage while continuing to report a verdict.

So `LIMITS` is now keyed on the renderer the run actually got. The GPU set is each pair's geometric middle, rounded: ratio 1 `perPose 0.18, mean 0.09`, ratio 2 `perPose 0.51, mean 0.26`. That is 2.5x over the fixed scene and 2.0x under the broken one at ratio 1, where the old limits on the GPU had 5.5x and 1.1x the wrong way round. The software set is untouched, so a fallback to software — every CI runner — returns the verdict it returned before.

Two things the measurement turned up that are **not** this work's doing and should not be attributed to it:

- **The software "fixed" row in the tool's header was stale by about a third.** It read `ratio 1 mean 0.14` from 2026-09-06; today's tree reads 0.095 on the same renderer. The broken arm reproduced 2026-09-11 to the digit (0.44 / 0.73 / 0.211 / 0.372), so the tree has not moved recently — the fixed arm improved somewhere between those dates and nothing re-recorded it. Both pairs are in the header now.
- **Ratio 2 is thin on both renderers and always was.** On software the fixed scene reads 0.51 against a 0.6 per-pose limit — 1.18x of room. The gate-proofs entry that warned about narrowing separation was looking at ratio 1; ratio 2 is narrower still.

`still 0.00%` on every pose at both ratios on the GPU, across two runs: **the GPU is frame-to-frame deterministic here**, which is what the "identical output twice" half of this gate requires and the one thing that could have ruled the move out.

### views: a sweep digest belongs to its renderer

Nothing in `views` is a verdict — it fails only on a page error, and its output is frames for a person to look at. It is now 11 s instead of 291 s, which is what the diagnostic meant to be run every iteration could least afford. The same tree gives sweep digest `b2e6a7395596` on the GPU and `beb2eef266b5` on SwiftShader, and the seven frames differ in mean luminance by 0.1 to 1.4 levels. **Every digest quoted in a review before today is a SwiftShader digest**, and a review comparing digests across the change is comparing nothing. The manifest names the renderer on its own line.

### shot and compare: two different reasons to refuse the switch

`shot` refuses it because the scored frame must be the same bytes here and on a runner, and a CPU rasterizer is deterministic across machines while a driver is not. `compare` refuses it for a reason that has nothing to do with 3D: it renders none, but it decodes and resamples both images through chromium's 2D canvas, and an accelerated canvas would make the scored digits a property of the graphics driver. Measured — the same three files decoded in a software-launched browser and in a `--use-angle=d3d11 --enable-gpu-rasterization` one come back **byte-identical**, with the scores equal to eight decimals. The lever is absent rather than defaulted because the measurement covers one machine and the contract covers every machine.

`shot` does now print its renderer through `rendererTag`, and — after the review pointed out that printing was not enough — **fails** rather than shooting when it is handed a GPU. That is the case that silently rewrites the contract: a GPU frame scores 0.0748 / 0.4742, inside the thresholds, so `compare` would pass it and `docs/PLAN-scores.md` would quietly begin describing a different image, on a green run. The throw lands in the tool's existing `catch`, so the render is removed rather than left for `compare` to score.

## What CI runs, and why its verdicts hold

`ci.yml` sets `GATES_GPU: 0` and `BLACKFRAME_GPU: 1`. The runner has no GPU, so without those lines every gate would ask, fall back and render through SwiftShader anyway — the same pixels by accident rather than by decision. With them:

- Every gate's chromium flags on CI are **exactly what they were before this change**: `WEBGL_ARGS` for shot, compare, placement, clearance, animation and nudge, and `GPU_ARGS` for blackframe, which has always asked. Nothing new is exercised there.
- `nudge` gets the software limits, which are the numbers it has asserted since 2026-09-06.
- `animation` gets a renderer margin of zero, so the worst frame is held to `docs/PLAN-scores.md` exactly as before.
- `record` is skipped, as it was.

The gate's own variable beats `GATES_GPU`, in both directions, which is what lets those two lines coexist; without that precedence the broader one silently wins and `blackframe` stops asking. Proved directly rather than assumed: under CI's environment, `wantsGpu` returns true for `BLACKFRAME` and false for `NUDGE`, `ANIMATION`, `PLACEMENT` and `RECORD`.

Both changed gates were then run on the CI path locally, `GATES_GPU=0 BLACKFRAME_GPU=1`:

- `animation`, three frames, fixed: cell 0.0749 to 0.0750, ssim 0.4733, motion 0.1807, against limits `0.0769` and `0.4678` — the same limits and the same verdict as before this work.
- `nudge`, fixed: `ok 0.095% <= 0.2%` and `ok 0.246% <= 0.3%` on the software set.

**What was not run:** a full `npm test` under CI's exact environment. That is the 10-minute SwiftShader suite, and the five gates it would have covered that the two above do not — `shot`, `compare`, `placement`, `clearance`, `blackframe` — either have no behaviour change at all or were A/B'd on both renderers individually. Worth saying plainly rather than implying coverage that was not taken.

## The scored path: three measurements and a recommendation

### 1. The GPU renders the photo view slightly better, and does it deterministically

`tools/shot.js`'s own code, launch flag as the only variable, scored by `tools/compare.js`'s own metrics on the same blank decode page:

| | cell distance | SSIM | sha256 | seconds |
| --- | ---: | ---: | --- | ---: |
| SwiftShader | 0.074947 | 0.473324 | `d29b76dd0272` | 63.1 |
| GPU, run 1 | 0.074844 | 0.474234 | `e166304bd4ae` | 6.3 |
| GPU, run 2 | 0.074844 | 0.474234 | `e166304bd4ae` | 6.8 |
| GPU, run 3 | 0.074844 | 0.474234 | `e166304bd4ae` | 5.9 |

Deltas: **-0.000104 of cell distance and +0.000909 of SSIM**, both in the direction that flatters the GPU. The three GPU renders are **byte-identical PNGs**, so this driver is deterministic run to run. The frames themselves are not close in the way the scores are: 348,221 of 1,320,000 channel values differ at the scoring resolution, the worst by 189 levels, mean |delta| 0.548 levels. The metrics are averaging that away, which is what they are for.

Against the margins the unit set — 0.0015 cell, 0.0030 SSIM against a 0.0010 cross-machine noise floor — **both deltas are inside, so local scoring on the GPU with CI as the SwiftShader arbiter is viable on this driver.** The SSIM delta is 0.0009, which is 91% of the stated noise floor: it is inside by arithmetic and not by much, and it is one GPU.

### 2. readPixels is four times cheaper and produces a different PNG

`shot` waits two settle frames and takes a compositor screenshot — three SwiftShader frames. One forced render at the pinned clock plus `gl.readPixels` over the whole buffer cost **8.4 s against 36.0 s** on the same page, with the readPixels itself 4.2 s of that.

The PNGs are **not** byte-identical, and neither are the pixels. The alpha channel is all 255 both ways, so that is not the difference; the difference is that the two paths encode different images. This was not pursued to the pixel because it does not need to be: the bytes differ, so the byte-for-byte contract `docs/PLAN-scores.md` rests on would have to be re-baselined to adopt it, and a 28 s saving on one gate does not buy a re-baseline of the scored frame. What `compare` reads off each is recorded in `out/scratch/swiftshader-frame.log`.

### 3. Where the SwiftShader frame goes — NOT OBTAINED, and the instrument is why

Two attempts, both defeated by the same three.js fault, so this is being reported rather than tried a third time.

The first probe called `__scene.render()` in a loop from a `page.evaluate` and three threw on the first call — `TypeError: Invalid value used as weak map key`, in `WebGLState.drawBuffers`, reached through `RenderPass.render` → `setRenderTarget` (`out/scratch/swiftshader-frame.log`). The second drove nothing itself: it timed the page's own `requestAnimationFrame` interval while toggling `Pass.enabled`, `shadowMap.autoUpdate`, `composer.setSize` and `renderTarget.samples` between measurements (`out/scratch/swiftshader-breakdown.mjs`).

**Its control failed, and that is the finding.** The last row re-measures the restored, shipped chain and should read what the first row read. It reads **0.02 s against 5.01 s**, and the page reported `pageerror: Invalid value used as weak map key`. The render loop had died partway through — almost certainly at the `renderTarget.samples` toggle, which is the same multisampled-target path the first probe hit — so from some point onward the probe was timing a loop that rendered nothing and reporting it as a frame cost. A dead loop and a fast one are the same number here.

What survives, and what does not:

- **The shipped frame is about 5.0 s at 1200x1100 on this machine's SwiftShader**, with a 1440x1320 composer target at **4** samples (the shipped 8, clamped) against a 1200x1100 canvas. This figure is quoted in `tools/lib/browser.js` and `AGENTS.md`, so where it comes from matters: it is the probe's **first** row, taken before any toggle and therefore before the failure, and it is corroborated twice from outside this probe: `animation`'s own per-frame line on SwiftShader reads `pose and two frames 15.4 s`, which is `setTime`'s synchronous render plus two loop frames — about 5.1 s each — and the whole shot path (one evaluate of two rAF plus a compositor screenshot) is 36.0 s.
- **That is not the same number as the 14 s this repo quotes**, and the two are not in conflict: AGENTS.md's 14 s is the cost of a ROUND-TRIP to the scene page, which waits out the frame in flight and then its own, plus CDP. The per-frame cost and the per-evaluate cost were never the same figure. Neither was re-derived here and neither should be changed on the strength of one contaminated run.
- **Every share in that table is void**, including the one that looks like an answer (`without the RenderPass 0.72 s`, which would make the base scene pass 86% of the frame). It is void on its own arithmetic as well as on the control: disabling any single post pass saves about 1 s, yet all four together would have to be worth 0.7 s. Those rows disagree with each other, which is what a broken instrument looks like from the inside. (The table also prints `without the ShaderPass` twice, at 3.98 s and 3.93 s — the chain has two `ShaderPass` instances, `sanitize` and `grade`, and the probe labels passes by constructor name. Harmless, and void with the rest.)

What a third attempt should do differently: never touch `renderTarget.samples` or `composer.setSize` — both recreate a multisampled target and both are on the path that threw — measure by `Pass.enabled` alone, and **re-assert the baseline after every toggle**, failing the run the moment it drifts, instead of checking the control once at the end where it can only tell you the whole run was wasted.

### Recommendation for the scored path: leave it on SwiftShader

Of the three options — SwiftShader as is, one-frame SwiftShader, GPU locally with CI as arbiter — **the first.** Not because the others fail their measurements, but because of what each costs against what it buys.

`shot` is 64 s of a 161 s suite. Moving it to the GPU would save about 57 s and would cost the property that makes the scored number worth recording: that it is the same number on every machine. The moment local and CI score different digits, every threshold in `docs/PLAN-scores.md` acquires a "whose renderer" qualifier, and the next person tuning the scene has to hold two numbers in their head. `animation` shows what the alternative looks like — it needed a whole margin constant, and that margin is measured on exactly one GPU.

One-frame SwiftShader is the weakest of the three: it saves 28 s, changes the scored bytes, and the second settle frame is there because this repo has twice shipped a gate that could not tell "rendered" from "rendered nothing".

If the suite ever needs cutting again, `shot` is the place to look and the lever is not the renderer — it is that `shot` and `animation`'s t = 0 frame render the identical frame twice, in two processes, for a total of about 70 s on SwiftShader and 1 s on the GPU.

### The fourth option: measured, put to the integration owner, and DECIDED AGAINST

**Decision (integration owner, 2026-09-15): the scored path stays on SwiftShader. This is settled, not open.** The reasoning of record: the number is only worth recording if it is the number CI verifies; the delta below is a property of *this scene's* sub-pixel geometry, which is exactly what every iteration changes; and nothing in the gates measures that delta, so a drift would surface as a CI red with no local reproduction. Sixty-three seconds does not buy an unmeasured channel to that outcome.

**The option that was weighed: `shot` on the GPU for every routine local run, and on SwiftShader only for the run that records the contract number at the end of an iteration.** CI is the arbiter on SwiftShader regardless, so what a routine local run has to do is predict CI's verdict, not reproduce its digits. It was never implemented, and the measurements are kept here so that the next person to have the idea reads the answer instead of re-measuring it.

What the measurement says it would cost and buy:

- **It predicts CI within the measured delta.** GPU against SwiftShader on the same tree, same code, launch flag the only variable: cell distance **-0.000104**, SSIM **+0.000909**, both flattering the GPU. Against the thresholds (0.0763 and 0.4703) the shipped scene has 0.0015 of cell headroom and 0.0039 of SSIM headroom, so the delta is 7% and 23% of the room the scene actually has.
- **It is deterministic on this driver.** Three GPU renders, byte-identical PNGs, sha256 `e166304bd4ae`, and the same digest again from `views`' own photo pose in a separate process. Nothing about the prediction is noisy run to run; the whole error is the one fixed offset above.
- **It saves 63 s of a 161 s suite** on every routine run, which is the largest single saving left anywhere in the gates.
- **What breaks if the delta drifts with a scene change, which is the real risk.** The delta is not a property of the renderers; it is a property of the renderers *and this scene*, and it is dominated by how alpha-tested sub-pixel geometry resolves — 30,000 blossom cards, the strand tubes, the tile ridges. That is exactly what iterations change. If a scene edit widens the SSIM delta from 0.0009 to 0.004, a routine local run scores 0.474 and passes while CI scores 0.470 and fails, and the failure arrives at push time with no local reproduction — the worst shape a gate failure can have. Nothing in the gates would notice the drift, because nothing measures the delta.
- **What would have to exist first**, therefore: a check that measures the delta rather than assuming it. The cheapest honest form is `shot` rendering both and failing when they part by more than a stated bound — which costs the 63 s back and defeats the point. The next cheapest is measuring it once per iteration rather than per run, which means a tool nobody is obliged to run.
- The same objection applies in a milder form to `animation`'s `RENDERER_MARGIN`, which this change did ship: it is the same crossing, measured once, on one GPU. The difference is that `animation` keeps the absolute thresholds underneath and CI still asserts them at margin zero, so a drift there shows up as a CI red on a gate that also runs locally — not as a number quietly diverging.

The decision rests on the drift, not on the delta. The delta passes every margin it was asked to pass.

## A second defect, found by accident, and the gate it became

Not part of the GPU work — found while the integration owner was poking at `tools/` on main. **`node --input-type=module -e "import('./tools/animation.js')"` started a full animation run**, browser launched and frames printing, and stopped only because someone killed it two minutes in.

The obvious suspect was `isMainModule` returning true when `process.argv[1]` is undefined, which would false-positive under any eval'd node. **That was wrong, and checking it first is why the real cause turned up quickly.** `tools/serve.js`'s version opens with `if (!process.argv[1]) return false;`, and that line earns its place for a different reason than the one suspected: `resolve(undefined)` *throws*, so without it an import from `node -e` would crash rather than be inert.

The real cause was simpler and larger: **seven tools had no guard at all.** `animation`, `compare`, `nudge`, `perf`, `placement`, `shot` and `test`, plus three diagnostics. Their whole bodies were module top-level code that ran on import — and `tools/test.js` was the worst of them, since importing it ran the entire suite.

The fix: `isMainModule` is exported from `tools/serve.js` now and takes the caller's `import.meta.url`, so a tool never hand-builds the comparison — hand-building it is exactly how `blackframe` and `record` skipped their whole main block on CI for three days in 2026-09. Each unguarded body is wrapped in `if (isMainModule(import.meta.url)) { … }`, **without re-indenting**, so the diff is three lines per file; across seven gate tools that is what makes the change readable at a moment when most of them could not be re-run.

**And it is a gate, not a note.** `npm run import-inert` imports every tool in its own child process, by the exact command that found the defect, and fails unless each exits 0, prints nothing and finishes fast. Promoting it rather than leaving a scratch proof is the whole lesson here: the defect lived in the one direction the gates never look — *no gate imports a tool* — so a proof nobody runs would have missed the next one just as completely. It costs about 7 s, opens no browser, and runs first in `npm test`. Red-proved by putting the guard back: the failure output is the reported defect itself, an import that launched a browser and started scoring frames.

Its other half is the evidence-marker check from 2026-09-09. This one catches a tool that runs when it should not; that one catches a tool that does not run when it should. Neither can see the other's defect.

## What a critic caught

One independent read-only lane ran over the integrated change and returned eighteen findings, three of them must-fix. Its two load-bearing confirmations first, because they are what let the rest of this document stand: **the t = 0 algebra is correct in both directions** (so the relative pair really is implied by the spread bound, and the absolute pair really did have to stay), and **CI's launch flags and limits are identical to `3854c75` gate by gate**, verified from `git show 3854c75:tools/*.js` and by executing `wantsGpu` under CI's environment.

The three that changed the code:

- **`RENDERER_MARGIN` made `animation` prove less on the GPU, and could never have been red-proved.** Written up in full above. This is the one claim in the change that was false, and the false sentence — "held two ways so that costs nothing" — was in the tool's header, in `AGENTS.md` and in this devlog. The margin is removed, all three are corrected, and the scored pair now carries its own honest bound in the tool: **it has no red proof and never had one**, because the fourteen-fold sway that reds this gate reds the motion bound while the scores print `ok`. That was true before this change too and nothing had written it down.
- **`isSoftwareRenderer` classified two real software renderers as GPUs, and one of them can reach CI.** `ANGLE (Microsoft, Microsoft Basic Render Driver Direct3D11 …, D3D11)` is WARP — where `--use-angle=d3d11` lands on a Windows box with no usable GPU — and nothing in that string says software. And `WebGL 2.0 (OpenGL ES 3.0 Chromium)` is what `src/main.js`'s `rendererName()` returns when `WEBGL_debug_renderer_info` is unavailable: it names no device at all. Either would have been handed `nudge`'s GPU limits, and today's software readings (ratio 1 close 0.20, mean 0.095) against 0.18 / 0.09 is **red on a healthy scene, with nothing in the log to explain it**. WARP now classifies as software; the masked string classifies as unrecognised, and `animation` and `nudge` stop rather than guess. All five cases were executed against the fixed classifier.
- **`nudge`'s header did not carry the one-driver bound** that `animation`'s did, and ratio 2 has only 1.24x of room per pose on the GPU set. It does now.

Two more the review raised that were acted on:

- **`shot` printed `[GPU, though software was asked for]` and carried on.** That is exactly the case that silently rewrites the contract: a GPU frame scores 0.0748 / 0.4742, inside the thresholds, so `compare` passes it and `docs/PLAN-scores.md` quietly starts describing a different image. `shot` now fails before writing, with a message that says which renderer it got, why that is not acceptable for this one file, and what to check.
- **`GATES_GPU=0` on its own moves `blackframe` to software**, silently, and a software run of that gate proves nothing about the driver fault it exists for. `ci.yml` pairs it with `BLACKFRAME_GPU=1` and always did; the gate's header now warns about the unpaired form.

Findings recorded and not acted on, because they are pre-existing or cosmetic: `nudge`'s `still` check can print `FAIL … 0.00%` (its test is `> 0`, its message is `toFixed(2)`); `tools/paintcheck.js` and `tools/shimmer.js` do not answer to `GATES_GPU` at all, and `shimmer` — the repo's own shimmer instrument — was not consulted when `nudge`'s shimmer baseline was re-derived, which is a miss worth naming; and the local suite now renders only the 8-sample configuration, so a **4-sample-only defect is caught by CI alone, and CI runs trimmed**. That last one is the real standing cost of this change and it belongs in the next person's hands, not buried here.

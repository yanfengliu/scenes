## clearance: a mesh is classified by what it is, not by what no list matched (2026-09-16)

- Claim (in the gate's own header, `tools/clearance.js`, under CLASSIFICATION): a mesh in the building set whose own name says it is a walking surface or a growing thing fails this gate.
- Origin: iteration 3 added `right walkway slabs` and `fence spill leaves`, and both landed in the building set. `tools/clearance.js` builds that set by EXCLUSION — anything `WALK`, `TERRACE`, `TERRAIN`, `LIVING` and `CANOPY` do not match is a building — and every one of those lists is a whole-name anchored regex, so a new mesh is never near a match. An independent critic reading the regex found it (`docs/devlog/detailed/2026-09-15-iteration-3.md`, finding 3); no gate did, and every assertion in the gate stayed green for a whole iteration. The consequence was that the terrace headroom rays dropped to the band under the paving rather than to the paving.
- Why a name check and not a list check: the name is written in `src/` and the set comes from the regexes in `measureInPage`, so the two facts are independent. A check built from the same symbol as the thing it checks proves only that the code agrees with itself.
- **E1, terrace paving back in the building set.** `right walkway slabs` removed from `TERRACE`, which is exactly the state iteration 3 shipped. Exit 1:

```

FAIL: 1 clearance problem(s):
  "right walkway slabs" is being treated as a BUILDING, but its name says it is a walking surface (the
  word "slab"). The building set in tools/clearance.js is built by exclusion, so a mesh no list matches
  lands there silently: swept for the street's clear-run rule, and — if it is paving — not counted as a
  surface anyone stands on, so the headroom rays over it drop to whatever is underneath. Put "right
  walkway slabs" in WALK or TERRACE in measureInPage (the lists are whole-name anchored, so add the whole
  name), or rename the mesh if it really is a building. If the word "slab" is wrong for this mesh, the
  word lists are SURFACE_WORDS and PLANT_WORDS at the top of tools/clearance.js.
```

- **E2, foliage back in the building set.** `fence spill leaves` removed from `LIVING`, again the state iteration 3 shipped. Exit 1, same shape: `— but "fence spill leaves" came through`, and `its name says it is a growing thing (the word "leaves")`. Both halves of the word list are therefore red-proved, not just one.
- Restored, `ok every mesh in the building set is named like a building: 184 scanned against 22 words`, exit 0, and `tools/clearance.js` back to sha256 `c7fdd664ea95ef66…`. (Both proofs were run twice: once on the 23-word list this check first shipped with, and again after `plant` was removed for the reason below. Had any of them differed, a manifest recorded on this machine would have reddened CI for nothing.
- Bounds, and the first is the big one:
  - **One command rewrites the manifest.** `--update "<reason>"` is the whole of the ceremony; the reason is required and must differ from the recorded one, and that is all. Nothing here can tell a considered update from a rubber stamp.   - **It pins populations, not correctness.** A right rename and a wrong one move a population identically.
  - **The site scan covers `src/*.js`, `tools/clearance.js` and `tools/placement.js`, and not `tools/namerules.js` itself** — a checker scanning itself would red on its own patterns. ## views: a pose is a fixed point of the frame loop, so its digest can be quoted (2026-09-16)

- Claim (in the gate's own header, `tools/views.js`): every pose is settled to a bit-exact fixed point of the frame loop's own `(controls.update, clampCamera)` pair before it is shot, so two runs of an unchanged tree on the same renderer produce the same digests; a pose that does not converge in 32 iterations is warned about by name.
- Origin: the integration owner, relaying the scene lane — pose 7's digest differed on every run, so the sweep digest a review is told to quote was a number that would not come back.
- Mechanism, measured rather than guessed (`out/scratch/pose7.mjs`, a per-iteration camera read-back). It is NOT a limit cycle. `clampCamera` pushes pose 7's camera out of the machiya's wall to a place the controls' own polar limit pulls back, and the two converge in three pairs — camera y `-2.030806` at the clamp, `-1.840034` after one pair, `-1.839704` after two, `-1.839703` after three, and bit-identical for the next seventeen. `views` gave it two rAF settle frames, and how many of the PAGE's own loop frames the compositor fits inside those is not fixed.
- **G1, the control, and it had to be made load-independent.** The defect is about frame timing and this machine is idle, so two runs coming out equal proves nothing. Instead pose 7 was rendered at each settle state on purpose (`out/scratch/pose7-bytes.mjs`), 0, 1, 2, 3, 4 and 8 pairs: **three distinct files** — `afcbdd84a749`, `2b375dfafa46`, and `b7834df3dad3` from 3 pairs onward. So the pre-fix path could emit any of three files for that one pose, and the sweep digest taken over all seven moved with it. (The probe takes no settle frame between setting a state and screenshotting, so the compositor may present a frame behind and the state-to-file mapping is not pinned; what IS established is that at least three distinct files come out of one pose, and that from three pairs on only one does.)
- **G2, the treatment.** Four `npm run views` runs on the fixed tool: sweep digest `454bd56f49b6` every time, and all seven pose digests equal to the ones `docs/devlog/detailed/2026-09-15-iteration-3.md` recorded (`d331cdc03f25`, `de79efde090a`, `02d2d22a0804`, `0e36ea98fbea`, `eea083d30414`, `ec6c6feea035`, `b7834df3dad3`). So the fix changed no framing.
- **It was not only pose 7, and that is the finding.** Pairs that MOVED the camera, per pose, on the shipped tree: 0, 0, 1, **10**, 0, 2, 6. (The loop applies one more pair than it counts and that last one is what proves the pose does not move, so zero is the healthy value.) **Four of seven** poses were being rendered at an unconverged state; only pose 7 was ever reported, because only pose 7 sits where the disagreement crosses a pixel boundary. A count whose floor is misunderstood by one hides exactly the cases nearest the floor.
- **Why no number of extra settle frames would have worked.** The loop's own frames are both what presents the canvas and what moves the camera, so a state cannot be pinned and presented at the same time. Only making the state a fixed point removes the choice.
- A line that was lying, found by adding the settle: `views` computed its "drift over the two rendered frames" note against the position after the FIRST clamp, so with a settle in between it reported the settle's own movement as drift. It now measures from the settled position.
- Bounds: the settle runs the loop's pair in ONE evaluate and the loop itself is not involved, so a defect that needs a real frame to appear is outside it; bit equality is the convergence test, so a pose that oscillates in the last ulp would exhaust the 32 and be warned about rather than fixed; and the warning is a warning — this tool is a diagnostic and fails only on a page error, so a non-converging pose still writes a frame and still enters the sweep digest.
- **Not proved red: the non-convergence warning.** No pose in this scene fails to converge, and no scene was built that would. It is a printed guard, not a tested one.

- The map's radiance and the contribution are measured ONCE, at build. Only the cheap half — the texture's identity, its shape, the intensity and the per-material binding — is re-read at the shot. - The shape check covers a height of 0 and a shape that CHANGES after the build. R2b measures that a wrong height present at build is covered by nothing.
- Measurement 3 reads a field three writes when it builds a program and never tests for invalidation, so its natural case is covered by the identity check beside it rather than by the count.
- `src/lighting.js` announces a failure with `console.warn('env: ...')`, every gate echoes it (`tools/lib/browser.js`, widened below) and `shot`, `compare` and `try` refuse on the state. - The field rate is zero. ### src/post.js: nine black pixels are a trigger, not a verdict

- **A bound the third arm states rather than hides.** `falseAlarms` only rises when the SECOND read comes back lit, so a driver whose default-framebuffer read returns black EVERY time never reaches the give-up path: `always-black` records falseAlarms 0, blind false, six ratchets, rung 4. An always-black read and a genuinely black canvas are indistinguishable to this module, and what covers the difference is `shot` refusing the frame rather than trusting the chain.
- **And the rate in the field, which is weaker than the arms and is reported as such.** 25 fresh `npm run shot` processes before the fix: **1 not the contract frame**. 25 after: **0**. That is NOT a measurement of the fix: the chance of zero failures in 25 runs at an unchanged 4% rate is **0.36**, the 95% upper bound on the post-fix rate from 0 of 25 is **11%**, and loop 3's ready times (18.1–20.6 s) never enter the range loop 2's flake sat in (14.5 s, the only run below 18.3), so it may not have entered the regime at all. What carries the fix is the forced arm, which is deterministic. The loops carry "no regression observed at n=25" and nothing more; an independent review corrected an earlier draft that read them as proof.
- Bounds: the arms force the PROBE'S ANSWER, not the driver, so this proves the decision procedure and not that the driver behaves as modelled; and `verifyComposer` reads the composer's two ping-pong targets, so a fault that is entirely in the final blit to the canvas is seen only by the second nine-pixel read.

## openScene: the wait still ends, four ways (2026-09-11)

- Claim (in the helper's own header, `tools/lib/browser.js`): `openScene` resolves the instant `index.html`'s `window.__sceneReady` settles, and otherwise ends — fast — on a module script that fails to load, on an uncaught page error, or at the readiness ceiling. It used to poll `window.__sceneState` every 100 ms, and on the scene page a poll is a `page.evaluate`, so the polls came back about one frame apart however short the sleep was: readiness was detected up to a whole 1200x1100 SwiftShader frame late, once per page, and `npm test` opens about a dozen.
- Origin: the suite-cost work of 2026-09-11. The saving is real — the same `shot` page reads `scene ready in 21.2 s` where it read 33.5 s — but it replaced a loop that checked three failure conditions on every turn with a `Promise.race`, and **no gate in this repo has ever opened a page that fails**. Every gate only ever opens `index.html` and it works, so a wait that could no longer fail fast would look exactly like one that can, on every green run, forever.
- Mutation: there is nothing to mutate — the failure paths are the thing under test. So four pages were built, one per way the wait must end, and `openScene` was pointed at each: `out/scratch/openscene-proof/` (`no-handshake.html`, `missing-script.html`, `throws.html`, `never-ready.html`) driven by `run.mjs`, which also opens the real `index.html` last and fails if THAT does not resolve.
- Failure produced, all five, with the time each took:

```
a page that is not the scene page            0.0 s  window.__sceneReady is missing, so this page is not
                                                    the scene page; index.html sets the handshake in an
                                                    inline script before boot.js runs
a module script that 404s                    0.0 s  a script failed to load:
                                                    .../there-is-no-such-module.js (net::ERR_ABORTED)
the page throws before the scene is ready    0.2 s  the page threw before the scene was ready: the scene
                                                    build blew up
the handshake is rejected, nothing thrown    0.2 s  the scene handshake rejected: the scene reported it
                                                    could not build
never becomes ready (ceiling set to 5 s)     5.0 s  the scene did not become ready within 5 s ... then
                                                    index.html's window.__sceneReady never settled
the real scene page                         13.6 s  RESOLVED
```

- The four fast ones are the point. The ceiling is 300 s, and it was raised to 300 s on the argument that a broken page still fails at once; these numbers are that argument, measured, for the first time. The fourth case exists because a reviewer noticed the first draft had four pages covering only four of six exits: `throws.html` reaches the *pageerror* arm, not the handshake's own rejection branch, and `rejected.html` calls `window.__sceneReject` directly with nothing thrown so only that branch can end the wait.
- **The sixth exit is not covered and cannot be**, and the tool says so where it is written: `scene state is "<x>", expected "ready"` needs the handshake to resolve while `__sceneState` says something other than `ready`, and `index.html` sets that field before it resolves. It is there for a future page shaped differently.
- The same review found that the new wait was **stricter** than the loop it replaced, in a direction nothing intended: the old loop stopped checking `requestfailed`/`pageerror` the moment a poll read `"ready"`, while the listeners here stay attached until the `finally`, so an error arriving between the handshake resolving in the page and the CDP response reaching node would have failed a page that was already up. An `armed` flag, cleared when `ready` settles and again in the `finally`, restores the old semantics. No error in this repo can fire in that window today, which is exactly why it would have gone unnoticed.
- Bound: **this is a proof, not a gate.** It lives under `out/`, which is ignored and regenerated, nothing runs it, and it will not notice the next change to `openScene`. The real page's arm ran at a 320x240 viewport, so it proves the wait resolves, not that the scene is right at any size. And it exercises `openScene` directly rather than through a gate, so it says nothing about whether a gate handles the error it is handed.

## nudge could not report a page error at all (2026-09-11)

- Claim (in `collectErrors`'s own header, `tools/lib/browser.js`): every console error, uncaught page error and failed request on a watched page lands in the caller's array, and `tools/nudge.js`'s `if (errors.length)` block fails the gate when one does.
- Origin: **not a defect this work introduced — one an independent review of this work found in the file it was touching.** `tools/nudge.js` held `errors = errors.concat(collectErrors(page))`. `collectErrors` returns the array it will push into; `concat` copies it *as it is at that instant*, which is always empty, and leaves the real one orphaned. So `errors` never grew, the check was dead, and this gate had never been able to report a console error, a page error or a failed request from the day it landed. Nothing would ever have said so: the gate passes either way on a healthy page, and on an unhealthy one it would have passed too.
- Mechanism, proved on its own in seconds with no scene at all (`out/scratch/collect-errors-proof.mjs`) — one blank page, one `console.error`, both patterns side by side:

```
old pattern (errors = errors.concat(collectErrors(page))): 0 error(s) collected
new pattern (collectErrors(page, errors)):                1 error(s) collected
  console.error: a console error the gate should have reported
```

- Gate-level mutation: `console.error('injected: a page error nudge must report')` added to `src/main.js` beside `window.__scene = api`, then `npm run nudge`. Exit 1:

```
FAIL: 2 page error(s):
  console.error: injected: a page error nudge must report
  console.error: injected: a page error nudge must report
```

- Two, one per device pixel ratio, which also shows the sink now collects across both of the gate's pages where the old code collected across neither. Restored, `nudge: 6 poses stable across device pixel ratios 1 and 2`.
- The same misuse is in `tools/paintcheck.js` (lines 94 and 105, `errors = collectErrors(page)` reassigned per page inside a loop, which drops every earlier page's errors). `paintcheck` is a diagnostic and is not in `npm test`, it was not touched by this work, and it has **not** been fixed or proved — it is named here so the next person does not have to find it again.
- Bound: this proves the plumbing, not the coverage. `collectErrors` watches `console`, `pageerror` and `requestfailed` and nothing else, so a page that fails quietly still passes; and it is attached per page, so work moved to a page nobody passed to `collectErrors` is unwatched — which is why `openInspector` takes the caller's array.
